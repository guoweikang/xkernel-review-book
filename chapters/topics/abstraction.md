# 重复功能与公共抽象

代码相似、功能重叠和适合共享实现并不是同一件事。
两段代码可能形式不同却承担相同职责，也可能形式相似却具有不同契约。

## 相同操作，不同契约

设两个模块都遍历一组对象并写出结果：

- 模块甲允许等待，要求全部结果写出后返回。
- 模块乙不允许阻塞，遇到资源不足必须立即返回。

这是一个假想例子。两者可能共享结果编码逻辑，但不能仅因为遍历结构相似就强行共用同一套等待策略。
需要分别确认数据格式、错误处理、资源生命周期与执行上下文。

公共部分可能是编码规则，差异部分可能是输出策略。Rust 的类型、泛型、trait 或组合可以表达这种分离；选择哪一种仍取决于接口和实现约束，不能据此预先认定性能收益。

## 可能的处理结果

| 情况 | 可考虑的处理 |
| --- | --- |
| 已有实现满足目标契约 | 直接复用 |
| 已有实现缺少一个合理扩展点 | 扩展已有实现并检查旧使用者 |
| 多个实现具有稳定的共同机制 | 抽取公共部分，保留差异 |
| 共同部分很少，适配成本很高 | 保持独立 |
| 契约、负载或依赖关系不清楚 | 补充证据后再决定 |

这是一种分析分类，不是自动判定规则。

## 公共模块之外的成本

抽取后公共模块变短，不代表系统整体更简单。调用方可能增加适配、参数和特殊分支。
评价方案需要同时检查公共实现、调用方、错误处理与迁移成本；性能比较也必须覆盖实际使用路径。

例如，为容纳模块乙而向共享接口加入大量模式开关，可能让模块甲也承担不需要理解的状态。
这种变化是否值得，取决于去掉的重复与新增的接口复杂度，而不能只比较删除了多少行。

## 候选发现与方案评价

重复功能分析可以拆为四个问题：

1. **定位**：哪些实现值得比较？
2. **生成**：有哪些复用或抽取方案？
3. **验证**：候选是否保持必要行为并满足约束？
4. **排序**：有效候选中，哪种取舍更合适？

比较评分方法时，候选集合差异会影响结果；比较完整系统时，检索和生成预算也会影响结果。
因此应分别说明评价的是评分器，还是整个分析流程。

## 全仓分析与增量分析

全仓分析寻找已有实现之间的关系，包括已经合入的代码。
增量分析则从修改出发，还需要确认哪些旧结论因接口、调用方或配置变化而失效。
