# 基础术语与概念

## 代码版本与变更

**仓库（repository）**保存代码和版本历史。**提交（commit）**标识一次版本记录，提交哈希用于定位版本。
**分支（branch）**是可以随提交移动的引用，因此记录分支名不足以固定一次审查对象。

**Pull Request（PR）**是请求将一组修改合入目标分支的协作对象，通常包含代码、描述、讨论和检查结果。
审查中的 **base** 是比较基准，**head** 是被审查版本。两者之间的差异称为 **diff**。
具体工具可能使用目标分支与源分支的共同祖先作为比较基准；不能只凭“与 main 比较”就假定比较范围相同。

diff 中的一段连续修改称为 **hunk**。新增行、删除行以及展示在旁边的未修改行分别承担不同作用：
新增和删除描述变化，未修改行帮助理解上下文。删除行属于旧版本，其行号不能拿到新版本中定位。

## 输入、规则与上下文

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| 需求 | 代码应当实现的行为或约束 | 请求取消后不得再交付结果 |
| 规则 | 审查采用的判断要求 | 所有取消路径都必须释放持有的资源 |
| 上下文 | 理解修改所需的相关信息 | 调用方、状态机、测试、配置 |
| 契约（contract） | 接口的前置条件、结果和责任约定 | 返回时是否已经复制输入缓冲区 |
| 不变量（invariant） | 在规定状态或操作边界必须保持的条件 | 已关闭对象不能重新进入可用队列 |
| 证据 | 支持某个具体判断的材料 | 调用链证明释放先于最后一次访问 |

上下文不一定构成证据。例如，一个名称中带有 `safe` 的函数提供了线索，却不能单凭名称证明生命周期安全。

## 审查方向与流程环节

**方向（dimension）**是检查什么：正确性、安全、性能、兼容性、文档或可维护性。
**流程环节（stage）**是怎样完成检查：准备输入、分析、验证、输出和处理反馈。

性能和兼容性可以同时检查同一修改，分别获取需要的证据。它们不是“先性能、再兼容性”的固定先后关系。

## 工具与配置

**静态分析**在不运行目标程序的情况下分析代码。**lint** 是这类检查中的诊断规则；
rustc 和 Clippy 提供检查，Dylint 支持加载自定义 Rust lint 库。Dylint 的动态库加载不等于运行时测试。
**测试**运行特定输入与环境下的程序行为，并检查结果是否满足断言。

Rust 的 **crate** 是编译单元，**mod** 是模块组织单元。**feature** 与 **cfg** 可以改变实际进入编译的代码。
因此“工具已执行”和“修改涉及的所有配置都被检查”不是同一件事。
本书中的 Dylint 与配置行为以 [X-Kernel 工程依据](../research/notes/2026-10-29-review-framework-evidence.md) 为参照。

## 意见与评价

**finding** 是一条具体审查发现，通常需要位置、触发条件、后果及依据。
**误报（false positive）**是报告了实际不成立的问题；**漏报（false negative）**是没有发现实际存在的目标问题。
**参照标签（reference label）**是评价时用来判断结果的标注，不因来自人工就天然正确。

**精确率（Precision）**关注报告中多少正确，**召回率（Recall）**关注目标问题中发现多少。
**采纳率**描述意见被采取行动的比例，不自动等于正确性。
公式、评价单位及例子见[评价指标](evaluation.md)，定义依据见 [Stanford IIR §8.3](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-sets-1.html)。

**严重程度**描述问题成立后的后果，**证据强弱**描述目前知道多少。后果严重不能替代触发条件的证明。
