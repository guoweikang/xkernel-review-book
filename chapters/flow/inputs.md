# 1. 输入与任务边界

审查的第一个问题不是“这行代码有没有 bug”，而是“正在审查哪个版本、按什么要求、回答什么问题”。
未固定这些信息，后续证据可能来自不同版本，或用错判断标准。

## 输入与输出

| 输入 | 用途 | 缺失时的限制 |
| --- | --- | --- |
| 任务类型、仓库、base/head 或扫描 revision | 固定对象与比较范围 | 无法确定问题是否由本次修改引入 |
| PR 描述、关联需求、问题报告 | 确认预期行为和修改动机 | 可以分析已有契约，但不能编造功能验收标准 |
| 适用规则及其版本 | 确认判断依据、例外和报告要求 | 不能把通用偏好冒充项目要求 |
| 文件清单、带位置的 diff 或全仓范围 | 建立检索入口 | 仅有 diff 摘要无法准确定位 |
| 平台、feature、构建与测试结果 | 限定有效配置及已有验证 | 不知道哪些代码实际受过检查 |

本环节输出的是带版本的审查范围、已有材料和缺失信息，而不是缺陷结论。
全仓扫描用固定 revision 和路径范围替代 base/head diff；它与 PR 审查共享分析方法，但没有相同的评论位置限制。

若任务还用于比较 reviewer，评价单位、目标问题范围、标签来源和预算也应在这里确定。
不能看到结果后再挑选有利指标；[反馈与评价](evaluation.md)负责收集和解释结果，不是到那时才定义成功标准。

## 先取 diff，还是先取规则？

两者回答不同问题。任务入口先确定仓库、版本和审查职责；规则决定必读材料和输出约束；
diff 揭示具体修改，再用于选取适用规则与上下文。它们可以分批读取，不必把所有规则和源码一次性装入模型。

例如，知道要做兼容性审查，可以先加载兼容性规则；看到 diff 修改了一个 syscall 的错误路径后，
才知道要读取哪一个接口的 man page 与 Linux 实现。反过来，规则也可能要求回查原先遗漏的配置文件。

## 不同方向需要不同输入

下表是按判断问题组织输入的分析方法，不是自动路由效果已经得到验证的算法。

| 审查方向 | diff 给出的线索 | 需要补充的输入 | 要回答的问题 |
| --- | --- | --- | --- |
| 功能正确性 | 新分支、返回值或状态变化 | 需求、问题复现、契约、调用方、边界测试 | 实现是否满足目标，而不是仅能编译？ |
| Linux/POSIX 兼容性 | syscall、errno、ABI、用户可见结构变化 | 目标兼容范围、man page、适用规范、固定版本的 Linux 参考代码 | 对同一输入和状态，用户可观察行为是否相容？ |
| 文档一致性 | 接口说明、示例或配置文档变化 | 对应实现、签名、默认配置、执行入口与测试 | 描述是否真实，示例是否对应实现？ |
| 性能与资源 | 分配、遍历、锁或数据结构变化 | 调用频率、规模上界、负载、平台与测量方法 | 新增成本在什么场景下有意义？ |
| unsafe 与并发 | 指针、锁序、发布或释放变化 | 所有权、调用约束、执行上下文、其他访问方 | 必要不变量是否持续成立？ |
| 复用与模块边界 | 新类型、模块或 crate | 现有实现、依赖方向、职责与生命周期 | 是重复能力，还是有必要的差异？ |

文件后缀只提供线索。文档修改可能改变公开契约；配置修改可能改变可达路径；一个公共 helper 的内部改动也可能影响 syscall。
因此不能把“非 syscall 文件”当作无需兼容性分析的充分理由。

## 三个具体问题

### 功能修改没有需求描述怎么办？

区分“代码现在做什么”与“代码应该做什么”。前者可以从实现推导，后者需要需求、已有契约或明确的项目约定。
若 PR 声称修复取消行为，却没有说明取消后的回调约定，审查可以定位歧义、请求补充；不能自行选一个约定后宣布代码违反需求。

### 文档改动是否要读代码？

纯排版修正通常不需要追踪实现。若把“返回前完成复制”改成“调用方须保持缓冲区有效”，就改变了使用契约，
需要检查实现及调用方。只检查新句子是否通顺，会遗漏文档和行为不一致的问题。

### 是否每次都读取 Linux？

不必。先确认用户可观察的兼容性是否受影响。涉及 errno、结构布局、阻塞或部分完成语义时，
查找对应接口的外部契约；需要解释边界条件时，再读相关参考实现。
Linux 内部实现不同不自动构成不兼容，参考版本也必须明确。

## 第三方方法

Google 的审查指南在 Context 部分要求把局部变更放回文件与系统背景，在 Tests 部分要求检查测试本身是否有效。
这是补充上下文的工程依据，不是让 AI 无限读取全仓的方案。[Google 检查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。

Bugbot 文档区分项目规则及路径作用域，并提供查看一次 review 实际加载、截断或遗漏规则的方式。
它提示了另一种输入问题：规则已配置，不代表完整进入了该次审查。[Bugbot 规则文档](https://cursor.com/docs/bugbot)。

## X-Kernel 的做法与依据

- 阶段 agent 从 PR 源分支读取规则；规则不可读时停止，而不是退回通用标准。
- 发现型阶段使用带标注 diff；Description 单独读取 PR 元信息并对照实际修改。
- POSIX 规则先确认适用范围，规定 man page、规范和 Linux 实现的查证顺序。
- Guidelines 检查代码与文档同步；完整 `docreview` 是显式入口，普通 review 不自动启动该审计。

这些是已核对的仓库规则要求，不代表已审计服务端每次都正确执行。
具体文件、版本与冲突记录见 [X-Kernel 流程依据](../research/notes/2026-10-29-review-framework-evidence.md)。

## 收获与尚不能推出的结论

上述设计让“该读取哪类材料”有了明确依据，并将规则版本与被审查分支关联起来。
但没有本项目的对照数据能说明它降低了多少漏报或 token；规则缺失、上下文截断和需求不清仍须单独处理。

后续的[对象拆解与方向分配](routing.md)决定哪些修改或存量对象进入哪些分析任务。
