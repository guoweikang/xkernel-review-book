# 2. 审查对象拆解与方向分配

一个 PR 可能同时修改实现、配置、测试和说明。方向分配的单位不宜只是文件，而应包含相关修改共同造成的行为变化。

## 输入与输出

PR 审查输入是固定版本的文件清单、diff、规则与初始上下文。输出是审查任务列表：每项关联修改位置、
审查方向、需要的材料以及尚不确定的关联。一个修改可以进入多个方向。

全仓审查没有必须依赖的 diff，可以按接口、模块、资源生命周期或功能候选组拆解对象。
此时应保存对象 revision、路径和关联关系，而不是伪造“本次新增行”。
跨模块的同一问题仍应关联起来，不能因为按目录拆分就失去共同契约。

## diff 处理要保留什么

- 保留原文件路径、旧/新版本和行号，分析摘要不能替代评论定位依据。
- 标记增加、删除、移动、生成文件与机械改动，避免大规模噪声掩盖小的行为变化。
- 将接口修改、实现、调用方、配置和测试关联起来；只按 hunk 切开可能打断契约关系。
- 分页或裁剪时记录未读取范围；缺失内容不能当作没有风险。

例如，PR 同时新增 feature 和修改一个 helper。只审查 helper 的默认配置，可能看不到新 feature 下才进入的调用路径。
这不是要求每次穷举配置，而是必须明确此次判断适用于哪些组合。

## 方向不等于互斥分类

一个等待路径的修改，可能同时影响正确性、性能和兼容性。可以分工查证，但不能因为分给性能 agent 就排除死锁或 errno 问题。
相反，同一根因也不必产生三条重复评论。方向分配与输出去重是不同环节。

## 第三方方法

Google 指南允许评审者只负责指定文件或特定方面，但要求说明审查范围。这是分工的责任边界，
不是证明未分配部分无风险。[Every Line 与 Exceptions](https://google.github.io/eng-practices/review/reviewer/looking-for.html#every-line)。
Bugbot 的路径规则提供了按变更位置关联规则的产品实例；路径匹配仍不能替代语义影响分析。
[Bugbot 文档](https://cursor.com/docs/bugbot)。

## X-Kernel 的做法与依据

`common.md` 要求先建立变更清单；Guidelines 按实现、API、unsafe、并发、配置等性质选择主题规范。
CG 的 `paths` 限定适用文件，`triggers` 提供新增/修改行的线索；带 `ai` 后端的规则进入相应 AI 判断。
具体字段及文档要求见 [流程依据](../research/notes/2026-10-29-review-framework-evidence.md)。

这提供了可维护的显式分工。尚未核实 xreview 服务端的实际路由实现，也没有方向分配召回率或 token 节省数据。
关键词未命中可能只是写法不同，不能据此推断不存在该语义风险。

## 深入问题

如何识别跨文件语义变化、如何分配有限上下文、如何衡量路由造成的漏审，属于本环节的研究问题。
进入 [上下文检索与分析](analysis.md) 后，分析结果仍可能要求新增方向或回查被略过的文件。
