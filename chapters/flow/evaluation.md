# 5. 反馈处理与审查质量评价

一条意见被修改、被拒绝、被撤回或长期未处理，表达的是不同事件。
评价 review 既要关注结论是否成立，也要关注遗漏、复核负担与后续行为。

## 输入与输出

输入包括逐条意见、对应版本、作者反馈、实际修复与复核标签。输出是意见的处理状态、评价数据及需要重新审查的范围。
新提交可能解决问题，也可能改变原证据；不能把旧版本的结论直接作为新 head 的结论。

## 处理状态不是正确性标签

“不修改”可能意味着误报，也可能意味着成本太高或暂缓处理；“已修改”也可能没有解决原问题。
用于评价时，要保存理由和观察窗口，并另行核验技术结论。

[精确率、召回率与评价单位](../basics/evaluation.md)给出公式和计数例子。
比较系统还需要固定任务集合与标签协议；不同项目上各自的采纳率不能直接解释为同条件质量排名。

## 第三方方法与研究

- Themis 研究如何从历史提交构造分维度质量偏好；它涉及标签筛选，不是所有 review finding 的正确性标注方案。
  [标签构建分析](../research/notes/2026-10-28-themis-reading-01.md)。
- Bugbot 报告的 resolution rate 判断评论是否被处理；它不能直接代替 Precision 或 Recall。
  [指标与限制](../research/notes/2026-10-29-bugbot-learned-rules-analysis.md)。
- Librarian 的人类偏好实验用于评价重构指标，与上述处理行为指标不同。
  [评价对象与实验边界](../research/notes/2026-10-27-librarian-reading-01.md)。

## X-Kernel 的做法与证据范围

`pr-ci-review` skill 描述了按 PR 查看 xreview 轮次、意见 ID、当前 head 状态和人工反馈的流程；
旧 review 摘要不能直接当作当前结论。[流程依据](../research/notes/2026-10-29-review-framework-evidence.md)。

这为跟踪反馈提供了文档入口，但本书没有完整历史意见数据集，也未审计服务端状态机。
目前不能报告项目的真实 Precision、Recall、低置信项价值或 token 收益。

## 深入：评价不只是一项总分

需要分别观察发现能力、意见正确性、严重问题遗漏、人工复核成本和运行成本。
如果优化减少了评论数量，却遗漏更多高后果问题，就不能仅凭 token 降低判断成功。
哪些反馈可以成为下一轮规则的依据，进入[知识沉淀](learning.md)环节。
