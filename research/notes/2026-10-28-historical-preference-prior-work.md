# 历史维护决策与质量评价：定向查新第一轮

日期：2026-10-28。阶段 A 基础调研；不采集仓库案例、不标注、不运行基线。
目的：核查 H01–H04 的既有技术，选择下一篇共同精读材料，不证明新颖性。

## 结论先行

“已合入提交作为偏好”“历史人工重构作为评价目标”“分质量维度评价”和
“保存评审中间版本”均已有直接先例。不能把这些概念本身作为创新点。
下一篇建议优先读 Themis §3：它最直接回答用户提出的已接受 PR/commit 方案。
再读 CodeTaste，辨析匹配历史设计和评价不同但合理的设计之间的区别。

## 已核对的最近邻

### P23 Themis（2026，v1）：最接近合入提交偏好方案

来源：[正文](https://arxiv.org/html/2605.00754v1)、
[作者数据卡](https://huggingface.co/datasets/project-themis/Themis-CodePreference)。
阅读范围：§3、§4.1、附录 B.3 相关段落与数据卡；未审计数据或复现。

从已合入 PR 中保留未回退的单文件提交，按质量维度分类，并用多模型共识过滤
混合意图。评价涵盖正确性、执行效率、内存效率、可读性/可维护性、安全。
训练与测试的提交采用时间及仓库隔离。八种评价语言不含 Rust。

与 H01/H03/H04 重叠：合入作为隐含人类认可、多维偏好、混合动机过滤、回退筛除
和隔离协议都已有先例。不能把这些作为新贡献。这里的回退过滤不等于分析回退原因。

待研究：合入及模型共识能否可靠支撑每一维标签？跨文件抽象是否需要更完整上下文？
数据含多种来源，不能称全部为人工逐对标注或全部有实际性能测量。
缺少 Rust 也不自动构成创新空间。

### P22 CodeTaste（2026，v1）：最接近历史重构选择评价

来源：[正文](https://arxiv.org/html/2603.04177v1)。
阅读范围：§2–3、§4.1、§4.4、附录 A.4 仓库列表；未完整精读或运行。

挖掘多文件人工重构，用历史补丁及 PR 信息生成任务，以 OpenGrep 规则和仓库
测试衡量意图实现；对齐分数为 Pass × IFR。区分详细指令与开放目标两条轨道。
附录列有 rust-lang/rust 与 ruffle-rs/ruffle，不能宣称这一方向尚无 Rust 对象。

待研究：不同但合理的抽象能否获合理分数？§4.4 已承认规则中的名称可能引入猜测。
Pass 使用前后版本重复执行后的通过/失败数量阈值，不是所有原来通过测试逐项保持
通过的证明。规则由模型生成，任务描述虽来自历史设计，仍不等于人工偏好真值。

### P24 CodeFavor / CodePrefBench（2024，v2）

来源：[作者项目页](https://llm-code-preference.github.io/)、
[论文版本](https://arxiv.org/abs/2410.03837v2)。
阅读范围：项目页的方法/评价说明与论文摘要；PDF 已取回不代表正文精读完成。

将 commit 前后代码经模型改写生成偏好训练对，另有基于 critique 的合成路线。
评价分正确性、效率、安全和人类偏好；效率使用性能测量证据，人类偏好单独收集。
这是演化记录到偏好及多维验证的先例，但合成对不能直接当作原始维护者的选择。

### P25 CROP：评审历史与完整源码快照

来源：[作者工件页](https://crop-repo.github.io/)。
阅读范围：About、Dataset Structure 与数据说明；未下载大型数据包或验证可构建性。

保存评审讨论、合入前中间版本、被放弃的变更及源码快照。
因此“记录同一 review 的多版本及理由”也不是新概念。数据提供研究材料，不自动
提供可抽象/合理独立的标签，更不能把 abandoned 当作设计低质量。

## 候选假设更新

旁支补充 P26–P28：Linux 去重取舍、OpenStack 评审理由、Quick remedy 回退研究。
具体阅读范围和访问限制见 [重构决策专题](2026-10-28-refactoring-decisions-sidecar.md)。
这些工作进一步说明拒绝理由和回退噪声分析已有先例；没有证据支持将其整体包装为新概念。

| 候选 | 已有先例 | 现在真正需要核查的问题 |
| --- | --- | --- |
| H01 历史偏好对 | Themis、CodeFavor、CodeTaste、CROP | 是否已把明确评审理由转成跨文件抽象选择的有条件偏好，并独立验证标签 |
| H02 过度抽象负例 | 拒绝重构研究由旁支专题核查 | 是否区分不该抽象、抽象方案不当和非技术拒绝原因；不是简单补负样本 |
| H03 多维证据 | Themis、CodePrefBench | 多配置/所有权约束下的证据如何影响选择，是否有超出一般多目标评价的机制 |
| H04 后续历史 | Themis 已过滤回退 | 是否分析回退的原因与需求变化，而不是只拿回退状态更新标签 |

这里列的是查新问题，不是已经找到的空白。单篇未覆盖某机制不代表整个领域没有。
本轮以论文和工件为主，未新增专利权利要求检索，不能据此得出可专利性结论。

## 下一次共同阅读

Themis §3，先问三件事：

1. 从一个已合入提交，到一条“某维度更好”的标签，中间做了哪些假设？
2. 哪些标签来自执行测量，哪些来自历史接受，哪些来自模型判断？
3. 当多个指标矛盾时，是筛掉案例、分维记录，还是给出综合结论？

CodeTaste 随后用于对照“历史选择一致性”与“工程质量”；Rust 安全抽取仍留给
REM/REM2 专题，不在本轮同时扩展实现路线。
