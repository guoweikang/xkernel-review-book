## 1. P30：拒绝条件本身也需要检验

[Detecting Overly Strong Preconditions in Refactoring Engines](https://leopoldomt.github.io/assets/pdf/2018-tse.pdf)，
IEEE TSE 44(5)，2018，DOI 10.1109/TSE.2017.2693982；在线发表 2017，卷期版 2018。
阅读范围：摘要、§3.2、§4.1、有效性威胁中的 oracle 误判段落；未逐项复核实验表。

论文研究重构器的过强前置条件：生成程序，收集被拒绝的变换；人工定位拒绝检查后，
在实验重构器中禁用相应检查并重试，用 SAFEREFACTOR 的前后差分测试查行为变化。
测试未发现差异时，将对应检查列为过强条件候选。该 oracle 有覆盖限制，作者报告过漏检
标准输出或非公开方法行为变化的情形。因此这不是完整等价证明，更不是让生产工具绕过安全检查。

对我们的方法推论：拒绝与弃答也必须接受独立核查。只看接受建议的精度，会奖励过于保守的系统。
诊断中必须区分必要约束、工具表达能力限制、证据不足与条件过强；不是看到拒绝就放宽约束。

## 2. P31：反例可以改变候选，而不只是给出失败结果

[Kayak: Safe Semantic Refactoring to Java Streams，v1](https://arxiv.org/html/1712.07388v1)，2017 预印本。
阅读范围：问题定义、§5 的合成—验证过程、目标语言及终止/异常边界；未复现或核对全部实验。

Kayak 面向 Java 集合循环到 Stream 的特定改写，用反例引导归纳合成（CEGIS）：
生成候选，检验约束，反例加入输入集，再搜索满足累计输入的新候选。
它使用特定 Stream 理论与不变量编码；文中对集合有界性和异常处理作出限制。
不能把该模型中的验证能力直接外推到任意 Rust 内核，也不能把我们的通用补证流程称为 CEGIS。

对我们的方法推论：必须明确“反馈改变什么”。执行输入反例改变候选程序，与阅读设计文档
澄清需求、确认配置、补充调用者信息是不同动作。既有反例驱动搜索已直接否定
“验证失败后换方案是新概念”的宽泛主张。

## 3. 把反馈问题分成三类

| 类型 | 已知与缺失 | 合适的下一动作 | 不应该做什么 |
| --- | --- | --- | --- |
| 方案确实违背已确认契约 | 有可核验反例或冲突 | 修改方案、缩小共享范围或拒绝 | 改写契约以让结果通过 |
| 是否违背尚不确定 | 版本/配置/调用上下文/覆盖不足 | 定位关键缺口，取得证据或暂缓 | 把没有测试失败当成等价 |
| 需求契约本身不明确 | 文档与维护者意图缺失或冲突 | 请求设计澄清，保留取舍 | 从现有实现自动推导“应该如此” |

此分类是本项目的协议建议，未认定新颖。前两类也可能同时存在；应按具体主张拆开，
而非给整个候选一个混合状态。工具不支持与证据不足可以导致相同的弃答输出，但原因及应对不同。

## 4. 对评价协议的增补建议

- 在独立标注的可行方案上，统计错误拒绝；在未穷尽方案空间的候选上，不声称测得完整漏报率。
- 对弃答分别记录待补证、工具不支持、需求待定和资源耗尽，报告补证后是否改变决定及其成本。
- 在同一证据池和预算内比较通用检索与前提驱动检索；基线也可调用工具，避免不公平信息优势。
- 不将多个没有独立性的检查通过次数累计成“更强证明”；记录各 oracle 覆盖的性质与共同盲区。
- 这批文献支持检查拒绝和反馈路径的必要性，不证明我们的机制优于现有方法。
