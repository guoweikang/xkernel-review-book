## 2. 先区分对象与适用性

| 对象类别 | 材料使用原则 | 不应自动施加的要求 |
| --- | --- | --- |
| 第一方生产 crate / 对外模块 | 复用现有设计、安全、rustdoc 规范；分析选定配置的真实边界 | 不以 package 总数直接充当合规分母 |
| crate 私有实现 | 使用父模块契约、源码和关系事实；候选差异无法解释时针对性补证 | 不要求每个私有函数单独设计文档或公共 API 格式 |
| trait / provider / callback | 分清调用者、实现者与框架义务；保留允许的定制行为 | 不能把一个实现的行为自动写成所有实现的契约 |
| host tools / tests / examples / benches | 标明角色、独立配置与用途；执行资料按真实运行环境记录 | 不照搬内核运行上下文要求；RD-002 默认不覆盖 example/test/bench/build script |
| vendor / 外部依赖 | 记录版本、来源、上游契约与本地补丁；核验本地使用条件 | 不为统一格式批量重写第三方文档 |
| 生成代码 / 宏展开 / 多配置实现 | 记录生成者、输入、配置及源码映射 | 不把无源码位置或单配置未出现当不存在 |

各对象可拥有多个角色，测试目录不意味着其中所有代码都不参与生产。
分类以 manifest target、实际构建和使用关系核实；A1 的物理目录仅为初筛线索。
全仓研究可以登记存量缺口，但不能据此在一个无关 PR 中要求补齐全部历史文档；
DD-002、SD-002 已明确区分全量审计、新增 crate 与存量 diff。

语言、链接和格式规则仍按原规范处理，但不是语义一致或值得抽象的充分证据。
相同错误枚举、相同字段类型、相同调用者类别，都不能单独证明两个实现可以互换。

## 4. 三层要求，不让每份文档承担全部责任

### 4.1 所有纳入分析的证据都要携带的属性

必需：证据标识、对象标识或未解析状态、源位置、版本、来源类别、适用范围、获取方式。
配置相关证据须带配置；配置不敏感需说明理由；配置未知则标未知，不使用“通用”掩盖缺失。
来源类别分为作者声明、静态提取、执行观察、人工判断、模型推断，推断必须保留依据。
每次验证记录执行者/工具及版本、条件、结果和局限，不能仅保存一个通过布尔值。
这些是采集/管理要求，不要求每段 rustdoc 手写 commit、hash 或工具版本。

### 4.2 分析对象的基础材料

需要定位职责、接口与实现、依赖/使用关系和配置范围。现有文档可以提供声明，源码可补线索。
文档缺失仍允许发现候选，但不得把猜测补成作者承诺；关键契约未知会限制后续结论。
每项材料状态至少区分：已取得、未取得、经限定范围检查未发现、不适用。
不适用需注明条件和理由；“不知道”不属于不适用。

### 4.3 由候选触发的补充材料

涉及 unsafe 才触发相关安全义务；涉及中断路径才核对相应上下文限制；
涉及泛型共享才展开可变化边界；涉及性能敏感行为才要求匹配工作负载的成本验证。
这并不取消原仓库规范，只避免研究工具为无关对象额外制造材料负担。
补证请求必须说明：缺少什么、为何影响当前判断、可接受的证据形式、补不齐时限制什么结论。
允许引用既有文档、测试或规格，禁止要求同一契约在 design、security、rustdoc 三处复制。

## 5. 核验与冲突处理

材料状态和主张状态分开：文件已取得不代表主张成立。
主张状态使用未核验、在限定条件下获支持、存在反证/冲突、已过期待复核；
每个状态均保留对应证据和范围，不把静态提取或一次测试统称为已证明。

冲突处理顺序：

1. 先排除版本、配置、对象映射和提取失败造成的假冲突。
2. 保留文档声明与实现观察，不以来源优先级自动删除其中一项。
3. 区分“实现实际如此”与“设计应当如此”；维护者确认契约，工具不能通过改文档掩盖 bug。
4. 关键冲突未解决，可以保留候选及补证请求，不能输出确定的安全替换结论。

例子仅用于解释协议，不是仓库实测缺陷：文档声明提交路径不分配，facts 显示调用某个分配接口。
先查是否同一配置、调用是否真实可达、是否仅初始化阶段执行；静态边本身不能证明每次提交都分配。
反过来，没有该调用边也不能证明无分配，尤其在间接调用或不完整制品下。
