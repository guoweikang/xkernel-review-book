# Auto-SCAT 原文分析：历史意见能否转成工具检查与免审依据

日期：2026-10-29。只分析 Auto-SCAT；不分析 Bugbot Learned Rules，不作创新性判断。

来源 ID：**P29，由主代理分配**，本旁支不另行创建编号。主代理已归档 [作者 PDF](../evidence/originals/P29-auto-scat-author.pdf)；本轮后续还读取了主代理提供的 `/tmp/auto-scat.txt`，复核 §3.2.3/§4.2 阈值描述。本旁支没有修改 PDF、来源台账或 manifest。

## 结论与可引用边界

Auto-SCAT 的实现目标是**把历史评审意见映射到已有 Checkstyle 检查，推荐启用检查或检查类别**。它有评论分类和配置生成两个层次，不是从评论合成新 checker，也不是自动证明某类问题已被工具完整覆盖。细粒度检查参数的自动配置被列为未来工作。[作者稿 §3、§7](https://mdipenta.github.io/files/Auto_SCAT_EMSE.pdf#page=8)

对我们的帮助是提供“历史意见 → 现成工具能力 → 配置候选”的方法参照。将其用于“工具覆盖后不再重复 AI Review”仍需另做覆盖、实际执行和例外核验；论文的配置精度不能直接当免审可靠性或审查问题覆盖率。

## 方法链与能力边界

依据：[§3.2–§3.2.3，作者稿页 8–12](https://mdipenta.github.io/files/Auto_SCAT_EMSE.pdf#page=8)。

1. **准备人工知识库。** 对带行号的 Gerrit 评论，寻找同一行上的 Checkstyle 警告，再人工判定评论是否真正对应检查。共址只是候选，不等于语义对应。特殊项目参数检查如 Regexp 被排除；某些数值阈值被设低以扩大候选。
2. **表示与匹配。** 对评论做字符清理、camelCase 拆分、停用词处理和 Porter stemming，以 TF-IDF/VSM 和余弦相似度匹配检查语料。知识库比较评论、评论加描述、无评论时补描述三种形式。
3. **分类与启用。** 达到相似度阈值后关联既有检查；项目内至少一条评论激活即可启用。可按单检查或整类别输出配置。研究以风格检查为主，不以一般 bug、设计重构推理为目标。

应避免的表述：

| 不宜写成 | 更准确的描述 |
| --- | --- |
| 从历史意见生成新静态分析器 | 选择已有 Checkstyle 检查/类别 |
| 学会项目全部规则与参数 | 利用评论证据推荐启用；自动学习具体参数留待后续 |
| 不需要人工标注 | 映射知识库依赖人工；只是目标项目配置过程自动化 |
| 将已采纳/已修复意见固化成规则 | 方法不要求原评论已经促成修复；评论表达的关注不自动等于组织共识 |
| 检查通过即可省略此类 AI 审查 | 论文没有验证这种免审策略 |

后两项特别重要：§2.3 明确不以是否改代码解决意见为条件；§6 承认评论建议可能未被落实。这不是历史偏好对或采纳监督数据。

### 分母分层

| 层次 | 数量 | 含义与不能外推的范围 |
| --- | ---: | --- |
| 六项目 inline 评论总数 | 31,594 | 不是全部进入人工映射评价 |
| 评论所在行产生 Checkstyle 警告的候选 | 7,989 | 表 1 称 CW Pairs；由工具预筛后的子总体 |
| 分层随机抽样并人工核验 | 1,872 | RQ1/RQ2 的主要人工参照样本 |
| 与 Checkstyle 检查对应 | 750 | 750/1,872 ≈ 40.1%，作者约写 40%；不是 40% 的所有评审可被自动化 |

六项目为 Couchbase、Eclipse CDT、Eclipse JDT Core、Eclipse Platform UI、OpenDaylight Controller、Vaadin；表 1 的历史窗口跨 2012–2017 年。两个项目相关样本仅 10 和 5 条，不能把其项目级高分视作稳定泛化证明。

**人工环节。** 两位独立标注者核验评论—检查映射，分歧由第三人协助解决。Mylyn 的配置参照另由研究者阅读编码规范建立。所读方法未给出可在本笔记引用的标注者一致性系数或分歧率；也不是项目维护者对自动配置的现场采纳实验。

**分割。** RQ2 按项目留一：五个项目构知识库，剩余一个评价，轮转六项目；不是随机按评论划分，更不是训练早期、验证未来的时间切分。RQ3 使用未进入前述六项目交叉验证的 Mylyn。

**校准边界。** §3.2.3/§4.2 开头宣称在知识库项目上校准阈值；但 §4.2 随后的步骤又将 withheld 项目的评论用作 ground truth，在其上形成随阈值变化的 precision 曲线并选折中阈值。这段没有明确区分内层校准 withheld 与外层测试 withheld，不能仅凭“五训一测”确认 nested 独立验证。步长为 0.1；§5 又比较整体曲线及逐项目最优阈值，采用 0.3/0.4，并报告表现较好的知识库形式。尤其 RQ3 改用“无评论检查也补描述”的形式。正文不足以无歧义重建全部嵌套校准、模型选择与最终测试边界；本轮未读实现，**不能宣称已经核实严格无泄漏，也不能据此直接断言存在泄漏**。逐项目最优分数应与固定阈值结果分开。上述文字已与主代理提供的本地提取文本再次对照。

### 配置启用（RQ2.2）

| 口径 | 精确率 | 召回率 | 评价对象 |
| --- | ---: | ---: | --- |
| 表 4，检查级，阈值 0.3 | 72.7% | 72.2% | 各项目启用的具体检查，与人工评论映射给出的应启用集合比较 |

## 局限与对“工具化覆盖免审”的意义

### 作者承认的限制

[§6–7，页 28–29](https://mdipenta.github.io/files/Auto_SCAT_EMSE.pdf#page=28)：人工映射可能有误；评论建议可能未被执行；稀少类别样本不足；阈值/预处理/知识库选择影响结果；仅验证 Checkstyle 与 Java/Gerrit 项目；存在词汇不一致或漂移；参数自动配置、更多工具和更多信息源属于后续方向。

### 本笔记的适用性判断，不是论文实证结果

- **可借鉴部分：** 将历史意见作为“值得核查哪些现成检查”的线索，并保留意见到检查的映射证据。它比只有自然语言规则列表多了一个可执行工具目录的落点。
- **证据断点：** 评论提到某规则 → 推荐启用 ≠ 已证明检测器语义覆盖该规则 ≠ CI 在正确版本/配置上执行 ≠ 未报警时可免审。论文没有完成后面这些证明，也没有测试取消 AI/人工检查后的遗漏。
- **仅有未报警不够：** 用于免审需要明确覆盖边界、参数、被扫描文件与配置、排除项/抑制、失败与未运行状态。否则“没运行”和“运行且无发现”容易被混为一谈。这是我们的后续核验需求，本次未实现。
- **历史意见不是最终规则：** 仍需处理过时意见、否定或撤回、单一评审者偏好、适用例外及维护者确认；论文不提供这些事实的可靠闭环。
- **精度与覆盖分开：** 不相关类分得好，只说明部分评论不该映射；启用类别正确，只说明配置方向符合参照。两者都不能给出一个具体 PR 中所有未查问题的数量。

### Rust 迁移边界

没有 Rust 数据或 Rust 工具评价，因此不能搬用论文的百分比。可迁移的是“目录化已有检查并匹配历史意见”的抽象流程；需要重新建立评论语料、检查映射与参数/例外协议。Checkstyle 的 Java 命名/Javadoc 等类别不能直接对应 Rust 的全部审查义务。所有权、unsafe 不变量、并发上下文、配置组合及跨模块契约是否有现成检查覆盖，必须逐项核实；本轮没有检查任何 Rust 工具当前能力，也不宣称某类工具一定能或不能覆盖。

## 未验证清单与下一步交接

1. Oracle.txt 的实际格式、标签粒度、多标签处理、分歧率及原始预测记录；未采集任何真实仓库案例。
2. 表 2 数值不一致、表 6 各行的准确分母与评价单位；截图请求失败，不把文本抽取当最终排版校验。
3. 训练/校准/模型选择是否严格嵌套，以及词表/IDF 的拟合边界；论文对不同配置的择优是否影响外部项目结果。
4. 可执行实现是否公开、工具版本与配置细节、工件许可证和可复现性；已确认的只是 oracle 记录入口。
5. 项目真实采纳、规则长期有效性、运行成本和免审后的残余风险；本文未报告相关受控实测，本轮也未实验。
6. 两作者 PDF 与正式期刊全文的版本差异；出版方页面本轮仅提供书目/摘要，正式全文未取得。
