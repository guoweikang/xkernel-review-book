# A3：优化判断的证据门槛

日期：2026-11-04。状态：研究协议草案，尚未通过案例试点检验。
承接 [A1 材料清单](2026-11-04-material-inventory.md) 与
[A2 元素规范](2026-11-04-evidence-requirements.md)，E01–E14 的含义以 A2 为准。
本轮定义判断权限，不运行优化实验、不新增生产规则、不把草案当作已验证方法或创新结论。

## 1. 判断对象与基本原则

判断对象不是“整个 crate 是否重复”的单一标签，而是一组实现中的某项职责或机制，
以及一个明确的复用/抽象方案。必须定位共同部分、差异部分和适用配置。
两个函数局部可共享，不代表两个模块应该合并；两个候选各自可合并，不代表三者可以共同合并。
每个阶段都允许保留独立实现，不要求所有候选最终产生补丁。

证据充分性依赖具体主张：材料齐全不等于内容正确；材料缺失也不阻止先提出有限的疑问。
下列 G1–G4 是证据判断层级，不替代研究 A–F 六阶段。
“必要”表示必须取得相应信息，不强制来自特定文档：可引用源码、契约或可核验的其他材料。
工具得分不能抵消安全、行为、配置或性能方面的关键冲突。

## 2. 四类判断及允许的输出

| 层级 | 想回答的问题 | 必要证据 | 条件触发的证据 | 允许输出 | 尚不能声称 |
| --- | --- | --- | --- | --- | --- |
| G1 候选发现 | 哪些实现值得比较？ | 可定位的实现及版本；至少一条可解释的功能或结构重叠线索；召回来源与范围，未知显式登记（E01/E12/E13） | 使用调用/类型/文档检索时保留对应 E02/E07 及来源；有名称线索但未核验职责时仅作检索线索 | 疑似共享某项职责的候选、相似依据、下一步问题 | 功能等价、重复实现不合理、可安全合并 |
| G2 共享可行性分析 | 是否存在值得探索的共同实现边界？ | 对齐相关职责、行为、差异、资源生命周期与使用方假设；明确影响可行性的未知项（E01–E04/E12） | 并发、安全、配置、资源成本、泛型和独立理由（E05–E10）按候选触及范围补齐 | 共同机制与定制边界；有依据的可行方向，或待澄清/不适合直接复用 | 尚无具体方案时声称存在可编译且无退化的重构 |
| G3 方案形成 | 怎样共享，为什么比不改更值得？ | 具体公共接口、差异承载方式、使用方迁移、依赖方向、可观察行为保留要求、收益与成本依据、验证计划（E02/E03/E04/E09/E11/E14） | 相关安全/并发/配置/性能验证义务（E05–E08），宏与间接使用的不确定影响 | 有明确前提及验证义务的方案；允许多个替代方案 | 没有实际补丁和结果就声称优化成功或性能不退化 |
| G4 补丁验收 | 这个实际改动在指定范围内能否接受？ | 方案对应的实际补丁及前后版本；验证义务的结果；行为与迁移检查；人工复核和剩余边界（E11–E14） | 触及的配置、并发、安全、ABI 和性能检查分别完成；无法验证的必要项保持阻塞 | 在明确版本、配置和验证范围内可接受，或拒绝/待补证 | 全仓无遗漏、所有配置正确、测试通过即普遍等价；系统不能自行授权合入 |

G2 的“可行方向”要求影响该方向的关键未知已解决；否则只能输出条件假设，不算通过 G2。
G3 可以形成尚待测量的方案，但必须明确标为待验证，不能计入成功优化。
G4 的接受由维护者确认，并遵循原有项目评审流程；本协议不构成自动合入或免审授权。

## 3. 各层级的退出、降级与阻塞

| 情况 | 当前处理 | 保留的研究信息 |
| --- | --- | --- |
| 只有名字相似，无法定位共同职责或实现结构 | 留作检索线索，不升级为有依据的 G1 候选 | 检索来源、未核实原因，不当作已确认误报 |
| 调用集合相似，但实际行为与使用条件未知 | 保留 G1，发出针对性补证请求 | 哪项差异会改变判断，证据取得成本 |
| 某个差异明确阻止直接替换 | 拒绝该替换方案；仍可研究局部共享机制 | 差异、冲突条件和被否定方案，不能泛化为所有抽象均不可能 |
| 文档、实现或配置相互矛盾 | 先核对版本与映射，必要时由维护者确认期望行为 | 冲突两端证据；不能简单选“更可信来源”抹除冲突 |
| facts 缺边、动态目标未解析或只有部分配置 | 限定已知影响范围；若影响安全或迁移完整性，阻塞相关 G2/G4 结论 | 未解析集合和未覆盖配置，不默认为没有使用者 |
| 没有匹配场景的性能数据 | 保留 G3 待验证；性能敏感方案不能通过 G4 | 需要的工作负载、指标、环境和预算 |
| 补丁减少代码，但增加公共接口负担或不必要耦合 | 比较保留独立、局部提取等方案，可能拒绝重构 | 减少量与新增维护成本分别记录 |
| 测试失败或必要环境不可用 | 区分补丁失败、环境失败、未运行；均不得写通过 | 原始日志、失败原因与补测安排 |
| 下游实现或契约变化 | 对受影响判断标记过期待复核，必要时降级 | 原结论、失效原因及重核范围 |

所谓硬冲突是针对明确方案和已核实约束的冲突，而不是模型表达的低置信担忧。
例如不能睡眠的路径与方案中必经的可睡眠操作冲突；但尚未确认该操作是否在此路径执行时，
应标记未知而非直接判定冲突。严重风险可以优先提示，措辞必须保留这一差别。

## 4. 验证义务如何产生

每项方案建立“需要保持的性质 → 受影响对象 → 验证方法 → 结果与局限”的对应关系。
验证方法先由风险与性质决定，不是先跑已有测试再将其解释为足够。

| 改动触及的方面 | 至少要考虑的验证义务 | 不足以单独证明的材料 |
| --- | --- | --- |
| 输入输出、错误及状态 | 正常/边界/失败行为，失败后状态与清理；必要时前后差分 | 仅编译成功或错误类型相同 |
| 所有权、Drop、unsafe | 资源转移与释放、不变量、调用者/实现者安全责任；适用的分析及人工审查 | 仅通过借用检查或复用同一指针类型 |
| 锁、回调、执行上下文 | 锁序、重入、是否允许阻塞、回调生命周期；适用的并发测试/模型及审查 | 单线程功能测试；动态压力测试也非完整并发证明 |
| 泛型、trait、分派或布局 | trait 义务、实际实例化、分派成本；若影响 ABI/布局需对应检查 | 一个实例可编译或仅看到函数签名相似 |
| feature/平台/模块依赖 | 列出受影响合法配置和依赖方向；按 Kconfig/kfeat 流程验证选定矩阵 | 盲目 all-features 或仅默认配置 |
| 热路径或资源成本 | 匹配规模和调用条件的基线/改后测量、重复次数、波动、相关指标 | 静态行数、调用边数量、一次更快结果 |
| 维护性与 clean code | 接口负担、职责一致性、定制复杂度、使用方修改、重复责任是否实际减少 | 单一删行比例或模型总分 |

试点后、最终测试前确定指标、重复测量协议及可接受性能边界；不得看到结果后调整通过标准。
任何样本的阈值须有需求或维护者确认依据，不统一规定所有模块允许同一百分比退化。
对互斥配置不能要求同时开启；未覆盖的有效配置写明，不把“计划测试”当作结果。
抽象导致 API/行为有意变化时，应作为另一个经授权的行为变更任务处理，不冒充等价精简。

## 5. 统一的候选判定记录

每条记录至少包含以下字段，格式实现尚未选定：

1. 候选标识、实现集合与局部职责范围、固定源码版本、配置和召回来源。
2. 重叠依据、差异列表、共同机制与定制假设；分别关联 E01–E14 的证据标识。
3. 当前层级与决定：继续、待补证、拒绝具体方案、限定范围接受或过期待复核。
4. 关键未知、反证及冲突；每项说明影响哪个判断，而非只列“置信度低”。
5. 拟议方案及保留独立的对照；预期收益、迁移成本和验证义务。
6. 实际验证记录：命令/工具、环境、结果位置、失败/跳过与覆盖限制；无结果则明确未运行。
7. 维护者意见、争议与仲裁；状态变更原因、时间及历史版本。

模型置信度不是正确概率。若以后输出概率，需要独立校准和检验；目前不设未经验证的总分阈值。
优先级可以综合潜在收益、风险和补证成本，但只决定先看什么，不决定什么算正确。
高风险证据不足的对象进入优先澄清队列；不能为了“降低漏报”把猜测写成事实。

## 6. 协议本身怎样接受检验

以下是 B–D 阶段的预定验证方向，本轮未执行：

- 构造缺失、陈旧、冲突及错误映射的材料，观察系统是否限制结论，而不是只测材料齐备的正例。
- 记录各层级的候选数、补证数、拒绝数、接受数和人工时间；大量弃答不能伪装高准确率。
- 对“拒绝直接替换但可局部共享”的案例独立标注，避免将方案拒绝误记为没有优化机会。
- 分别评估候选召回、共享判定、方案有效性、实际补丁收益；不将跨阶段错误混成一个分数。
- 保留原始材料条件、人工补充条件和自动提取条件，计算获得证据的成本及抽取误差。
- 对独立测试冻结门槛；协议因试点修订时保留旧版本与理由，不回写原始标签掩盖分歧。
