# 注释辅助克隆检测：算法与评价口径精读

日期：2026-11-09。研究对象：Kuttal、Ghosh，*Source Code Comments: Overlooked in the Realm of Code Clone Detection*，[arXiv 2006.14505v1](https://arxiv.org/html/2006.14505v1)。本轮读§II-B、§III–V及表I/II；核查部分参考文献，不声称完整审计。PDF和提取文本保存于 `research/evidence/runs/2026-11-09-comment-clone-reading-01/`，版本与哈希见其中provenance.json。未运行作者实现。

## 1. 算法不是“大模型主观打分”

作者将一个源文件的注释作为文档，用LDA学习主题分布，再将文件分到主题组，作为疑似克隆集合。处理包括排除版权文本、去HTML标签、停用词和标点、规范化、构造词典及文档词频矩阵。此处的注释范围比rustdoc广，不能直接将原实验称为API文档实验。

LDA的经典出处是[Blei、Ng、Jordan，JMLR 2003](https://www.jmlr.org/papers/v3/blei03a.html)。它提供概率建模基础，但模型中的“某文件属于某主题的概率”并非“两个实现行为等价的概率”。本次仅核对经典论文书目及摘要，未逐式审计其推导。目标论文也没有提供一个可直接照搬的、经过校准的Rust重构价值分数。

本文对照是Java的JPDG与GRAPLE，聚焦文件级克隆，不直接推荐抽象方案或验证重构。作者从GRAPLE结果中排除同文件内克隆及重复文件组合，使输出适配文件级任务；这并非完整展示该工具在其原始方法级任务上的能力。

## 2. 两种评价口径不能混读

设真实克隆组为G，预测组为C，U表示取所有组的文件并集。按§III-C的Method 1描述，可重写为：

```text
P_file = |U(C) ∩ U(G)| / |U(C)|
R_file = |U(C) ∩ U(G)| / |U(G)|
```

这里检验的是“哪些文件参与了克隆”，不是“哪两个文件互相构成克隆”。这是对论文流程的数学重述，不声称已从作者代码核验具体实现。

一个用于说明指标性质的自构反例：真实组是{A,B}和{C,D}，预测组却是{A,C}和{B,D}。文件并集完全一致，P_file和R_file都是1；但预测的两个文件对均错误。此例不是论文数据中的实际错误，也不证明其原始结果无效，只说明该指标不能证明配对质量。

Method 2保留组，对每个预测组寻找与真实组最匹配的结果，再平均。正文未清楚规定precision与recall冲突时如何选同一个最佳组、是否一对一匹配及空组处理，复现时不能自行补齐后称原样复现。

表I报告：

| JHotDraw方法 | Recall | Precision |
| --- | ---: | ---: |
| LDA Method 1 | 94.86% | 84.21% |
| LDA Method 2 | 28.61% | 88.57% |

两行还分别使用100和105个主题，输出组数也不同。因此不能把数值差全归因于评价方式，更不能把Method 1的94.86%直接称为功能重复配对召回率。

## 3. 真值、调参与复现缺口

- §III-D报告由高年级本科生和研究生使用Java Compare、Eclipse构建真值，JHotDraw投入45小时，跨语言部分55小时。文中报告克隆组规模，但本轮已读部分未见完整标注准则、独立双标一致性和争议裁决记录；“两个人参与”不自动代表每项独立双标。
- 315个JHotDraw文件中5个无注释，LDA只处理310个。对我们而言必须报告缺文档覆盖损失，不能静默排除后当作全仓效果。
- 文中讨论主题数、passes、iterations的调整，并引用此前工作选择主题区间。未见独立留出评价的充分说明；复现须区分作者设定与我们的开发集调参，不能在同一测试集上挑最好结果。
- 混合路线讨论了LDA与PDG集合的共同文件及缩小输入范围；本轮未找到完整“筛选后重新运行PDG”的质量／耗时对照表。因此只记为方案与集合分析，不当作端到端加速已验证。
- §IV中还出现不同上下文下的文件数与集合记号，不能仅凭表I的组数重建TP/FP/FN。须取得原始组和标签，才能复算指标。工件就绪状态另列，不用正文缺信息推断作者没有工件。

## 4. 对xkernel实验的具体决定

**保留的研究假设：** 文档主题可以补充词法结构之外的候选信号。**不接受的捷径：** 同主题就是功能等价；相同文件召回率代表相同配对质量；已发现克隆就是值得重构。

先准备文献可追溯的最小基线，而非马上训练大模型：

1. 核查作者工件和原始标签能否复跑；可取得时先复算原口径，再附加配对评价。取得失败则记为“按论文重实现”，不冒称复现原数值。
2. 接入固定源码的原生文档，保存绑定对象和原文；分别记录函数、模块、crate级别与文档缺失率。既有33函数调用语法输入不包含全部外围文档，不能直接当文档语料。
3. 以token基线、简单文档检索和论文主题路线比较；Rust适配是新实验，不沿用Java指标数字作为目标阈值。
4. 将候选输出统一成可审阅的对象对。主题组若展开为所有两两组合，要固定展开和预算规则，大组不能免费获得更多审阅机会。函数对与文件对分开报告，部分共享关系未必具备传递性。
5. 对标注充分的固定评价范围报告pairwise precision/recall；检索采用precision@k和固定审阅预算下额外确认数。全仓真值未知时不报全仓recall。保留文件覆盖作为辅助指标，不代替正确配对。
6. 在开发数据上固定参数和随机种子方案，独立测试不再调参；记录多次随机运行波动、去文档／打乱文档控制和同源代码隔离。

原18对是已看答案的开发案例，适合确认实现和暴露失败，不用于论文主效果。新指标安排是实验设计，不是已验证的新算法。优化价值仍需独立对照实际补丁的行为、性能与维护结果。
