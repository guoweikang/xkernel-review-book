# 公共抽象与 Rust 重构：有边界的补充文献核对

检索及核对日期：2026-10-27。性质：本轮规划的证据补充，不是系统综述、新颖性判断或项目评估协议。

## 结论与范围

**“公共骨架 + 差异参数化”已有直接先例。** Wrangler 将克隆类反统一为公共函数，并生成各实例对应的参数化调用；Stitch 从程序语料学习可复用抽象。Rust 的函数抽取、所有权及生命周期修复也已有 REM 系列工作。不能把这些能力重新命名后作为新颖性主张。具体依据和适用边界见下列五项来源。

本轮读过仓库根 `AGENTS.md`，以及已有的[初步研究](2026-10-27-initial-research.md)、[范围修正](2026-10-27-scope-and-abstraction.md)和[来源台账](../SOURCES.md)。仅补充此前较薄弱的抽象生成及 Rust 落地证据；不重复检索通用克隆检测、RAG review 或专利。本目录下未发现更深层 `AGENTS.md`。

阅读为指定正文章节和表格核对，并非五篇全文精读；未运行作者工具、复验数据或检查证明实现。下文区分作者报告、明确实现限制和本项目待检验问题。“本轮未见评估”不表示整个领域无人研究。没有进行 X-Kernel 源码扫描，因此**尚不能认定本仓库已经存在某种抽象、性能或维护瓶颈**。

## 五项一手来源及实际阅读范围

### W1 — Li、Thompson，FASE 2011：Incremental Clone Detection and Elimination for Erlang Programs

原始入口：[作者机构书目信息](https://www.cs.kent.ac.uk/pubs/2011/3087/)；[作者 PDF](https://www.cs.kent.ac.uk/pubs/2011/3087/content.pdf)。机构页面题名含 “Code Clone”，PDF 题名不含 “Code”，是同一工作。

- **阅读范围：** 引言中的反统一定义；§4 中输出、排序及增量缓存；§5 克隆消除；§6 与表 1；§7 相关工作定位。未逐项验证完整检测算法。
- **覆盖：** 用公共项及各实例替换表达差异，输出公共函数与调用实例；按参数、返回值数量及函数体大小排序。支持克隆类、跨模块宿主选择，以及按函数区分结构变化和位置变化的增量更新。§5 已明确讨论功能边界、命名、宿主模块和人工选择，不能说它“只看语法，不考虑架构”。
- **评估：** 三组 Erlang 代码：Wrangler、工业测试套件、编译器及 stdlib；约 24–252 KLOC，比较全量/增量时间及克隆类数量。表 1 的测试套件初次检测为 560 秒，明显慢于更大的编译器/stdlib；作者归因于候选数量和规模。
- **限制：** §6 明说无法给出具体召回率。“100% precision”针对其静态语义感知克隆定义，不能解释为所有建议都值得采纳。Erlang 实验也不能证明 Rust 迁移可行。

### W2 — Thompson、Li、Schumacher，Programming 2017：The pragmatics of clone detection and elimination

原始入口：[期刊页面](https://doi.org/10.22152/programming-journal.org/2017/1/8)；[作者预印本 PDF](https://arxiv.org/pdf/1703.10860)。

- **阅读范围：** 研究方法说明；§4 工具行为；§5 案例关键步骤，尤其 Step 3、5–7；§6 经验讨论。未完整阅读第二案例及全部后续工具演化。
- **覆盖：** 项目范围检测与针对选区的搜索；公共函数和调用实例报告。案例中主动选择较小而有职责意义的片段，也因参数过多、难以命名而保留多个函数。宏差异曾需手写泛化；抽象顺序可能需要内联后重新概括。公共骨架不是必须采用检测器给出的最大片段。
- **评估：** 与 Ericsson 工程师合作的 Erlang 工业案例；作者明确使用参与观察和定性分析。本轮具体核对的案例对象是 SIP 消息处理测试套件。
- **限制：** 这些观察支持“存在这种工程决策及障碍”，不能估计所有项目的发生率或量化长期维护收益。作者的半自动流程不是全自动最佳模块设计器，但也绝非完全忽略可维护性。

### W3 — Bowers 等，POPL 2023：Top-Down Synthesis for Library Learning（Stitch）

原始入口：[出版 DOI](https://doi.org/10.1145/3571234)；[作者 v2 正文](https://arxiv.org/html/2211.16605v2)；[实验语料入口](https://github.com/mlb2251/compression_benchmark)（本轮只确认论文链接，未检出或运行）。

- **阅读范围：** §2 抽象库迭代示例；§3.1 表示与匹配；§6.1–6.2 实验设计/结果；§6 对高阶扩展的说明及 §7.3。未审查附录证明、剪枝实现或全部消融。
- **覆盖：** 在 lambda/DSL 表示中搜索带抽象变量的公共结构，用实例参数替换；反复学习、重写形成分层抽象库。既有语料整体抽象已有先例，不仅是逐对比较。基础匹配是受限的语法驱动等价；论文也讨论与演绎重写结合以增强高阶抽象，不能笼统说其所有版本都不支持高阶函数。
- **评估：** 五个 DreamCoder 领域比较压缩、时间及内存；另一实验为绘图/积木规划的八个子域，各 250 程序，含训练/测试划分。报告的数量级加速限于这些任务和对照。
- **限制：** 抽象质量主要按压缩衡量；这不是 Rust 内核的维护价值、运行性能或模块边界正确性评估。该表示中的可重写性不能直接充当 Rust 副作用和所有权保持的证明。

### W4 — Thy、Costea、Gopinathan、Sergey，OOPSLA 2023：Adventure of a Lifetime: Extract Method Refactoring for Rust（REM）

原始入口：[出版 DOI](https://doi.org/10.1145/3622821)；[作者 PDF](https://verse-lab.org/papers/rem-oopsla23.pdf)。

- **阅读范围：** 方法概述、实现段；§4 实验设计、结果、失败与运行成本；§6 讨论。未逐条核验 §3 所有推导规则。
- **覆盖：** 将函数抽取拆为初始提升和控制流、所有权、生命周期等修复；利用分析及编译器反馈恢复有效签名。它处理选定片段如何抽取，不等于自动发现全仓库应共享的职责。
- **评估：** 五个 Rust 项目、40 个案例，包含历史人工抽取、内联再抽取及选取片段；成功 37 个。成功判据包括编译及人工行为检查，不能概括为只测编译，也不能当成机器证明。比较对象是 2023 年版本的 IDE 插件。
- **限制：** 正文记录泛型 trait 约束、字段简写等失败；参数化有时过多。§6 将更惯用的数据类型方法提取及增强约束支持列为改进方向。本轮未复现，不能将旧插件结果外推到今天。

### W5 — Britton、Pak、Potanin，2026 预印本：Refactoring and Equivalence in Rust（REM2.0）

原始入口：[作者记录](https://arxiv.org/abs/2601.19207)；[本轮核对的 v1 正文](https://arxiv.org/html/2601.19207v1)。不据此声称已获同行评审。

- **阅读范围：** 架构概述；§4.6 支持边界表；§5.4.2–5.4.3、表 5–6；§5.5、表 7。未审核 Coq 脚本或附录的可信计算基础。
- **覆盖：** rust-analyzer 抽取/修复，加可选 CHARON/AENEAS/Coq 等价检查。
- **评估：** 新特性集合 40 例成功 33 例；动态 trait 对象为 1/4。验证集合特意筛掉不支持特性，含十个基本案例与十个简单真实函数；表 7 和正文显示第 20 例失败，不能写成“20/20 证明成功”。
- **明确限制：** 单文件视图可能缺少跨模块 trait 信息；验证链不支持 unsafe、函数指针/闭包及内部可变性等，嵌套借用也受限。这是该版本验证链的边界，不是所有 Rust 重构工具的能力边界，更不是当前 AENEAS 最新状态。抽取成功与可验证必须分开计数。

## 最接近技术对照：已有覆盖与本项目待验证差异

以下是基于上述来源的任务映射，不是新的实验发现。W1–W5 的原始链接和证据范围均见对应条目。

| 本项目设想 | 最接近的已核对覆盖 | 仍须在 X-Kernel 验证，不能先当贡献 |
| --- | --- | --- |
| 公共骨架 + 差异参数化 | W1 的反统一、公共函数、实例替换；W3 的抽象学习 | 公共机制是否真实存在；差异能否表达为值、类型、trait/关联类型、闭包或独立策略；接口是否比原实现更难维护 |
| 全仓库与增量入口 | W1 全量与增量；W2 项目检测与定向搜索 | 多配置 Rust 分析的覆盖率；配置、宏、依赖与契约变化后的失效传播；是否保持全量/增量结果一致 |
| 多份实现组成能力组 | W1 克隆类；W3 多程序共同抽象及层次库 | 跨函数/模块职责是否可组合，局部重叠如何分组；避免由两两相似误推整组可共用 |
| 给出合理优化建议 | W1 排序与宿主选择；W2 参数复杂度、职责及人工裁决 | 维护收益、迁移成本、代码体积、编译成本和运行性能分别有什么证据；保留独立实现是否更好 |
| Rust 定制实现及行为保持 | W4 签名修复；W5 受限片段等价检查 | 生命周期、Drop/清理顺序、锁和 IRQ 上下文、unsafe 前提如何保持；受支持子集之外如何记录未证明义务 |

反统一只是把不同实例解释成一个更一般结构。即使两个实现能由同一参数化函数表示，也仍需回答该函数是否拥有一致职责、差异接口是否合理，以及迁移是否保持行为。这个区分在 W1/W2 已有工程依据；不能将“考虑上下文和边界”本身说成首次提出。

## 给主线程的瓶颈线索，而非项目结论

本轮可定位的**既有系统障碍**是：W1 的候选密度影响检测成本；W2 的过度泛化和命名/职责问题；W4/W5 的签名重建失败；W5 的验证子集限制。它们比“现有方法都只看文本”更具体，也更容易被反驳或复验。

主线程可据此先收集本仓库的反例和真实失败记录，而不预设需要新算法：

1. 候选过多还是候选遗漏？分别定位索引、候选匹配和语义核验成本，避免把耗时统一归因于全仓库规模。
2. 候选是否本来就应独立？检查同一职责下的执行上下文、资源所有者和错误恢复；公共部分应放在现有 owner 边界内，不能因减少重复而引入反向依赖。
3. 抽象卡在何处？区分共同结构找不到、接口表达不合理、Rust 类型检查失败、配置不可用、行为保持未证实以及收益不足。
4. 若声称改善效率，究竟是检测器更快、迁移更省人工，还是内核运行更快？这些目标不能用压缩率或抽取成功率互相代替。

以上仅作为本轮计划的证据输入；样本选择、指标、基线和评估协议由主线程统一决定。本补充没有生成重构方案、实现工具或认定仓库 finding。

## 尚未核对与停止边界

- 没有复验五篇工作的原始数据、源码及形式化证明。W1 的 precision 声明、W3 的速度优势、W4/W5 的成功率均保留原任务边界。
- 没有完整精读 W2 第二案例、Stitch 的高阶扩展/全部消融、REM 的完整分析规则及 REM2.0 证明附录；不能据此评价它们所有输入上的正确性。
- 本轮未展开 Java 克隆消除、PDG 方法、一般 anti-unification 历史、DreamCoder/babble 原论文或 trait 抽取专门研究。W3 的相关工作已经提示其他抽象学习路线，故不能把本文五项当作穷尽检索。
- 未核对当前 rust-analyzer、REM 系列或 AENEAS 最新实现状态；实际基线选型应固定工具版本，再测本仓库的 Kconfig、宏、no_std、多架构及跨 crate 上下文。
- 未核对 X-Kernel 任何候选组的可抽象性、热点性能和长期维护负担。先找可复验的现有失败，再决定是否研究新方法；文献中的空白描述不替代本项目证据。
- 本轮停止于“已有公共骨架先例、抽象选择的工程证据、Rust 落地边界”均有正文支撑。进一步扩展应由实际候选中的失败类型驱动。
