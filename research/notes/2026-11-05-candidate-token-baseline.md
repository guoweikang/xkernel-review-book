# P01：候选发现的 token 基线边界

**1．范围与主源。**2026-11-05，直接以 `pdftotext -layout` 读取归档 `research/evidence/originals/P01-sourcerercc.pdf`，定向核对 §2、§3.1–3.4 及 §4.3–4.4、§5 的评估边界；未通读其他部分。归档为 *SourcererCC* 的 arXiv:1512.06448v1（2015-12-20），[作者原文固定版本](https://arxiv.org/pdf/1512.06448v1)，manifest 记录下载入口为 `https://arxiv.org/pdf/1512.06448`。本轮仅本地阅读，查询词为 `overlap`、`filter`、`precision`、`recall`、`THREATS`；未扩展检索、未运行检测，不改变研究六阶段或预定贡献。

**2．重叠是什么（§2、§3.1）。**比较对象是代码块；每块表示为带频次的 token 多重集，不是执行轨迹。token 包含关键字、字面量、标识符，字符串按空白拆分，运算符不计入。重叠为共享 token 数（保留频次），判定条件为 `|Bx ∩ By| ≥ ceil(θ × max(|Bx|, |By|))`，不是 Jaccard 的并集分母。块内原语句次序不是这个相似度的组成部分。§2 将 Type-4 定义为语法不同但功能相同；不能把 token 阈值克隆直接解释为功能等价。

**3．索引与过滤如何省比较（§3.2–3.4）。**按统一全局 token 顺序排列，语料稀有 token 优先；对长度为 `t` 的块，只索引长度 `t − ceil(θt) + 1` 的前缀，建立 token→代码块的部分倒排索引，查询也从前缀取候选。Sub-block overlap 性质提供必要条件：满足所需重叠的块，其相应前缀必须至少相交一次；相交并不充分。Token position filtering 再用“已匹配数 + 两侧剩余 token 数的较小值”作为可达重叠上界，不足阈值即可提前排除，达到所需匹配数可提前接受。这里的 position 是统一排序后的 token 位置，不是原源码控制流；过滤保证针对既定 token 相似度，不是保证不漏掉语义重复。

**4．评估支持到哪里（§4.3–4.4、§5）。**论文以克隆基准评估召回；在 BigCloneBench 实验检出的约200万对中随机抽390对，人工确认355真、35假，报告 precision 91%。三位专家分担核验，不应写成每对均经三人独立一致确认。原文说明标识符名称未归一化，跨项目改名会影响阈值召回；较弱 Type-3 和 WT3/T4 召回较差，Type-4 检测不在研究范围。误报包含相似 API 用法但用途无关、断言形式相近却测试不同行为；§5 保留配置选择与人工判断主观性威胁，对照工具 precision 采用已发表值而非本实验统一复测。因此91%是该抽样的“克隆”判断比例，不是 Rust 功能重复准确率，更不是重构安全率。

**5．用于 Rust 的候选基线：推论而非实证。**可借鉴 token 多重集、部分索引和过滤，作为可解释的词法候选召回支路；阈值重叠说明的是共享词法材料，适合与后续语义证据分层。§3.2脚注仅报告当时实现 Java/C/C# 的语言感知扫描器，并提出可扩展性；本文不猜测工具当前是否支持 Rust。Rust 落地仍需核实块边界、宏展开、条件编译及 token 规则；本轮没有相关实测。相同 token 可对应不同控制流/效果，低 token 重叠也可能实现同一功能；所有权、生命周期、副作用、并发、配置与性能等不能由这条基线确认。故命中仅支持“值得比较”，未命中不证明不存在功能重复，也不授权抽象合并或免审；候选单位与质量评估协议由主线程另行整理。
