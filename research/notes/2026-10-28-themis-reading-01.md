# 共同精读 02：Themis 的质量标签从哪里来

日期：2026-10-28。来源 P23，版本 v1（2026-05-01）。
[原文 §3](https://arxiv.org/html/2605.00754v1#S3)。原文副本已在证据清单保存。
本轮开始共同讲解 §3，不把此前预读算作用户已理解或认可；仍属阶段 A。

## 研究对象

区分评价代码的模型（Themis-RM）、训练偏好数据（Themis-CodePreference）和
评价这些模型的基准（Themis-CodeRewardBench）。本轮讨论第三者的标签来源，
不是完整 PR 合入决策或评论生成系统。

## §3 的提交挖掘链

基准混合已有数据与新挖掘提交，并非全由已合入 PR 构成。新挖掘部分依次：

1. 从开放许可仓库选单文件代码变更。
2. 用质量维度检索词获得样本，训练 ModernBERT 分类器召回相应变更。
3. 用 PR 数据保留已合入、未回退的提交；仓库活跃度等作为信誉代理。
4. 多模型共识过滤多意图或意图不清的变更。
5. 为剩余代码对反向生成任务指令。

评价维度包括功能正确性、执行效率、内存效率、可读性/可维护性和安全。
表 1 明确区分多模型验证的提交偏好与执行验证等其他数据来源，不能说每个
性能偏好标签均有实测支持。§3 未提供我们已核实的“全部标签正确”保证。

## 本轮教学解释与待验证问题

- 单文件限制有利于缩小上下文和归因范围，但不保证只有一种改动意图；可能遗漏
  跨模块抽象，因此这是取舍而非通用最佳筛选条件。
- 分类器判断变更属于哪类，不等于独立证明该维度实际改善。
- 合入状态和未回退提供维护过程信号，不自动证明所有维度都提升。
- 多模型一致不等于多位独立维护者认可；模型可能共享偏差。
- 反向生成指令帮助形成统一评价任务，但不必然还原开发者当时的完整需求。

教学假设（非采集案例）：增加缓存可能降低计算耗时但占用更多内存；在耗时维度
偏好新版本，不等于在内存维度或所有工作负载下也偏好新版本。

本轮要点：评价标签应理解为“在给定要求和维度下倾向哪个候选”，而非代码的
无条件优劣或 PR 的最终批准。读者讨论尚未完成，不新增已确认创新点。
