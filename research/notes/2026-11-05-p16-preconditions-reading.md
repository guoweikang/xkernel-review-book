## 1. 作者究竟在判断什么

输入是 Java 克隆片段，目标变换是抽出共同方法、将差异参数化，并调整未匹配语句的位置。
方法先对齐嵌套结构，再对相应程序依赖子图做语句映射，最后检查变换前置条件。
不是简单计算相似度后超过阈值就合并，也不是搜索所有可能的公共库设计。
§3.3.4 说明使用嵌套结构分治降低匹配组合爆炸风险，但某些大量可互相匹配的结构仍有成本问题。

前置条件是“某个变换要保持行为必须满足的条件”。它与相似度回答不同的问题：
相似度帮助找到值得比较的实现，前置条件检查这种改写会不会破坏依赖或控制流。
作者的可重构性结论属于其变换、分析模型和支持范围，不能解释为所有语言及抽象方式的通用判定。

## 2. 最重要的例子：参数化会改变求值位置

§3.4.1、Fig.5 的原例先读取对象字段，再调用会修改该字段的方法；两个版本的方法名不同。
如果为了共享，把不同的方法调用直接放到公共函数的实参位置，调用会在进入公共函数之前执行。
这样可能变成先修改、后读取，破坏原先的读后写顺序。名称和类型匹配不能避免这个问题。

四种依赖的直观解释：

- 数据依赖：后一步使用前一步写出的值。
- 反依赖：先读后写同一位置；交换后，读到的值可能变化。
- 输出依赖：多次写同一位置，顺序会影响最终值。
- 控制依赖：操作是否执行依赖前面的分支条件。

作者条件 1 要求参数化不得破坏相关控制、数据、反及输出依赖；还讨论循环携带依赖等情形。
这些是具体的行为保持检查，不是“让 AI 再检查一下有没有风险”。

对 Rust 的启发是我们的推断，不是本文结论：应区分传入已经计算好的值与传入稍后执行的操作。
闭包/trait 策略可能保留操作位置，但还需要核对捕获、借用、执行次数、Drop、锁与性能；
不能把改成闭包视为通用修复。现有 X-Kernel 调用关系本身也不足以重建完整的路径及依赖证明。

## 3. 八条前置条件，以及不能照搬的地方

| 条件 | 论文中检查的内容 | 对本项目的启示与边界 |
| --- | --- | --- |
| 1 | 参数化差异不得破坏相关依赖 | 要检查求值位置、次数和条件，不只比较调用集合 |
| 2 | 不同子类统一到共同父类后，使用的方法必须由共同父类提供或在子类重写 | 需要检查公共接口是否承载所有使用要求；Java 继承规则不直接等于 Rust trait 规则 |
| 3 | 被参数化的差异字段不能被该片段修改 | 对应 Java 按值参数下的字段赋值问题；Rust 可变引用可能表达不同方案，但必须另外验证 |
| 4 | 被作为差异实参参数化的方法调用不能返回 void | 是作者值参数变换的限制；不是 Rust 单元类型或操作回调不能抽象的证明 |
| 5 | 未匹配语句可移到公共片段前或后，且不破坏依赖 | 部分重叠不等于可以任意搬开差异代码；必要时缩小共享范围 |
| 6 | 抽取后最多回传一个、两侧类型一致的局部变量 | 作者讨论包装对象方案，但认为会增加结构成本；不能将多输出本身判为普遍不可抽取 |
| 7 | 抽取片段不含条件性 return | 作者讨论返回标志再让调用方退出，但指出增加分支复杂度；Rust 控制流编码须另评 |
| 8 | 被抽取的 break/continue 必须带上对应循环 | 检查控制流出口和目标，不把抽取后能解析等同于行为不变 |

§3.5 当时实现只处理两个克隆片段，讨论组级扩展及规模风险。
不能将旧实现的成对限制说成整个领域只能两两处理，也不能用两两兼容证明整组有共同方案。

## 4. 对现有研究协议的修正

对 [G1–G4](2026-11-04-optimization-evidence-gates.md) 的主要补充是把“失败”分成三类：

1. **所选变换会破坏行为。** 例如提前求值；拒绝该方案，保留失败证据。
2. **当前变换器不支持该表达方式。** 例如只允许一个返回变量；记录能力限制，不标为无任何优化机会。
3. **可以编码，但代价不值得。** 例如增加包装类型、标志与额外分支；比较维护成本和其他方案。

同一个候选可以对值参数方案失败，对保留执行位置的策略方案尚待验证。
因此判断单位应进一步显式包含“变换方式及版本”，而不只是代码对和一个可重构布尔标签。
现有 A3 已区分拒绝具体方案与拒绝所有抽象机会，本篇给出一手机制依据，非新增实验结果。

对应 E 元素：E03/E04/E05 需要关注求值/控制/状态依赖；E09 记录差异承载方式；
E11 将前置条件关联到核验方法；E14 记录为了抽取新增的接口和控制复杂度。
不能因此要求所有作者在 rustdoc 手工绘制依赖图；静态分析处理可提取事实，
文档提供调用者必须了解的契约，未覆盖的行为保持问题由验证义务显式记录。

## 5. 查新与后续问题

已有前置条件检查、差异参数化、语句移动约束、表达能力与复杂度取舍的直接先例。
因此“给重构增加条件”“保留不同实现”“关注 clean code”都不足以构成创新主张。
后续真正需要核查的是：证据缺失或冲突时，已有系统如何确定检查顺序、取得补充证据，
以及是否据此改变具体变换方案，而不只是一次静态检查返回拒绝。

本篇并未证明 P16 不具备其他功能，也没有核对其当前后继工具。

作者改用字段参数化等特定处理后重测失败对，通过既有测试。这不是独立留出集结果或完整行为证明。
这还说明外部持久化契约可能超出局部依赖模型，下一步需定向追踪证据缺失与变换选择的直接先例。
