## 已有工作与启示

| 工作 | 已核实的内容 | 对本项目的意义 |
| --- | --- | --- |
| [SourcererCC, ICSE 2016](https://arxiv.org/abs/1512.06448)；[作者仓库](https://github.com/Mondego/SourcererCC) | 基于 token 和索引的可扩展克隆检测，支持多个代码粒度。 | 文本/结构克隆适合作为独立召回通道；不能由此证明可替换性。 |
| [SCIP](https://github.com/scip-code/scip)；[Sourcegraph precise navigation](https://sourcegraph.com/docs/code-navigation/precise-code-navigation) | 定义、引用、实现等代码导航索引；Rust 使用 rust-analyzer。 | 可复用符号事实抽取底座，但功能、执行上下文与生命周期契约需要另建模型。 |
| [RepoCoder, EMNLP 2023](https://arxiv.org/abs/2303.12570) | 通过迭代检索与生成利用仓库上下文完成代码。 | 仓库级检索增强本身已有研究；任务是补全，不是复用审查。 |
| [GraphCoder, 2024](https://arxiv.org/abs/2406.07003) | 使用控制流和依赖关系组成的代码上下文图做粗到细检索。 | 图结构检索可借鉴；不能把它的补全指标当作审查正确率。 |
| [Recommending Clones for Refactoring Using Design, Context, and History, ICSME 2014](https://cormack.uwaterloo.ca/~migod/papers/2014/icsme14-wei.pdf) | 使用设计、上下文和历史特征推荐值得重构的克隆；明确并非所有克隆都应消除。 | “检测相似”与“建议复用”的区分、上下文打分均有先例。 |
| [LAURA, 作者提供的 ASE25 论文](https://yuxiazhang-bit.github.io/papers/ASE25_LAURA.pdf) | 结合变更上下文、审查样例检索与指导生成 review；案例包含借助扩展上下文发现重复代码。 | diff + 检索 + LLM review 已有很近的工作，需要更具体的贡献。 |
| [jscpd semantic clones](https://jscpd.dev/guides/semantic-clones)；[boundaries](https://jscpd.dev/guides/boundaries) | 官方文档描述实验性函数向量克隆检测（含 Rust）及模块/目录/方法边界规则；同时承认相关函数会被误报为克隆。 | 应纳入工具基线；“语义克隆 + 边界”这一宽泛组合不能作为未经检索的新颖点。 |
| [SonarQube metrics, 2025.1](https://docs.sonarsource.com/sonarqube-server/2025.1/user-guide/code-metrics/metrics-definition) | 区分整体代码和新增代码的重复度等指标。 | 增量质量门已有实践；重复行比例不等于值得复用的概率。 |
| [Google: Static Analysis](https://abseil.io/resources/swe-book/html/ch20.html)；[Tricorder, ICSE 2015](https://research.google.com/pubs/archive/43322.pdf) | 强调增量审查、开发者可行动性和 effective false positives。 | 除正确率外应测量无效提醒负担，但作者未采纳不能自动当作技术误报。 |

## 评价研究中的警示

[Krinke 与 Ragkhitwetsagul, 2025](https://arxiv.org/html/2505.04311v1)
检查了 BigCloneBench 中 406 个 Weak Type-3/Type-4 样本对，报告其中 93%
缺少相似功能。这个数字针对该抽样及作者判据，不能外推成整个数据集的错误率。
论文仍认可该数据集用于原定的语法/文本克隆检测目的。对本项目的启示是：
不能把功能类别、克隆标签或高 embedding 相似度直接当作“应该复用”的真值。

[Semantic Code Clone Detection: Are We There Yet?, 2026 预印本](https://arxiv.org/abs/2606.25272)
报告 11 个检测器在经语义保持变换构造的分布迁移样例上性能下降。
本文仅核对其摘要层面的实验描述；不能据此认定任何工具在 X-Kernel 上的表现。

## 建议的任务定义

给定固定 PR HEAD、比较基线、构建配置和新增/修改实体，检索当时已有的实现，
判断是否存在能满足新增需求并遵守项目边界的复用途径，输出可定位的证据和建议。
它包含重复实现发现、复用可行性判断和评论价值判断，不追求一般程序等价判定。

第一阶段范围建议为仓库内实现及已声明依赖的可用 API；全生态第三方库推荐另作扩展。
避免要求新增代码与某个既有函数一对一对应：一个新模块可能重复一组已有 API 的组合，
也可能只重复部分能力。需区分直接复用、局部扩展、抽取共同能力以及合理独立实现。

X-Kernel 当前 `docs/ai/review/guidelines.md` 的“复用已有抽象”已经要求提供既有实现
位置，证明相同数据/不变量/格式，并豁免分层隔离、依赖方向和独立演进。
`CG-041` 专门覆盖已有安全边界抽象。新系统应为这些判断提供证据，未来再决定规则迁移，
而不是现在新增一条“相似度高即违规”的规则。

## 元数据建议

实体包含 crate、mod、struct/enum、trait、impl、函数/方法；父子包含关系形成层次。
只索引前三类会漏掉实际可复用的函数和 trait，也容易用一个粗略模块摘要掩盖差异。

| 字段组 | 内容与来源 |
| --- | --- |
| 符号事实 | revision、符号标识、路径与区间、父实体、签名、字段、可见性、引用和实现关系；由工具抽取。 |
| 功能职责 | 输入/输出、操作对象、职责与非职责、资源/状态所有者；来自 rustdoc、设计文档及带证据的模型推断。 |
| 使用契约 | sleepability、IRQ/NMI、锁、分配、生命周期、unsafe 前提、错误语义、复杂度和 ABI 约束。 |
| 可用性 | 架构、cfg、Kconfig/kfeat、依赖方向、循环依赖、可移植性边界。 |
| 可追溯性 | 每个判断的源码证据、抽取方式、工具/模型版本、内容哈希、覆盖范围和 unknown 标记。 |

工具事实、文档声明、模型推断分开保存。缺少契约是 unknown，不等于允许调用。
索引保存关系不意味着一开始必须采用图数据库；先确定查询与证据模型，再比较存储方案。
SCIP/rust-analyzer 是候选抽取层，需要先验证本仓库 Kconfig、宏和多架构构建的覆盖。
宏生成内容须追溯到源码/宏定义；无法解析的分支要报告覆盖缺口，不能视为没有实现。

索引可由基线快照加 PR overlay 构成，搜索时包含未修改代码和 PR 内其他新增实体。
最终判定必须回到固定 HEAD 的实际代码；处理删除、重命名、移动和替换，避免把搬迁当复制。
缓存至少区分 revision、配置/目标、解析器与模型版本；调用方/契约变化可能使派生摘要失效，
不能只因实体自身文本哈希未变就复用全部判断。目标分支后来的实现不能被当作 PR 当时已有。

## 多路检索与判断

建议流程：diff 定位完整实体 → 多路召回 → 候选集合合并/去重 → 契约及依赖检查
→ 局部替代方案分析 → 证据分级 → AI review。

召回通道包含 token/AST 克隆、名称/字段/ABI 标识的词法搜索、职责语义向量、
引用/数据流/所有权关系。取候选并集，而不是要求每种相似度同时高。
crate/mod 分数应基于可映射子职责的覆盖及重要性，不取所有子项相似度的简单均值。

“局部替代方案分析”要求回答：改用哪个 API 或哪组 API、参数和状态如何映射、
保持哪些不变量、需要哪些适配、还有哪些无法满足的要求。它是可审查的工程论证，
不是 LLM 给出的程序等价证明。编译通过也不能独立证明功能和上下文等价。

优先使用离散标签：可直接复用、可扩展已有实现、需共同抽象、合理独立实现、证据不足。
相同队列算法但一个允许睡眠而另一个运行在 NMI，是重要的困难负例；
相同 ABI 字段的重复转换若能通过既有 owner API 完成且满足上下文，是候选正例。
这些是设计例子，不是对当前代码的已验证 finding。

## 打分与校准

分开记录检索相似度、契约兼容性、架构可行性、适配成本和证据完整性。
初期允许可解释的序数排序；不把向量余弦或 LLM 自报分数解释成概率。
明确契约冲突时，不发布“直接复用”建议；可能的共同抽象应另行举证。
unknown 候选进入补证流程或暂不评论，不能被高文本相似度抵消。

积累人工数据后，可学习“在当前变更中值得提出复用建议”的排序/概率，并在独立验证集
校准阈值。模型的置信度、问题影响和评论优先级分别记录；不可将几个相关的子分数
直接相乘并宣称概率。评论预算、预计维护收益和误报处置成本属于产品策略，需显式定义。

## 评估方案

1. **检索质量**：Recall@K、首个可用候选排名、实体/能力组覆盖率。区分单实体和组合复用。
2. **判断质量**：各标签 precision/recall、困难负例误报率、弃答覆盖率与错误率、概率校准。
3. **Review 价值**：每 PR 无效提醒数、可行动评论精度、作者接受/拒绝原因、review 耗时、
   定位正确率、P95 延迟、索引更新成本和模型 token 成本。接受率不能替代技术正确性。

数据包含历史复用修正、真实新功能 PR、合理独立实现、移动/抽取/跨架构实现和语义保持变体。
历史未被重构不能直接标负；历史改动已合入也不自动证明原实现应复用。
人工至少独立双标并仲裁，保留任务契约和拒绝理由；按 PR/克隆家族、时间及子系统分组切分，
避免同族样例泄漏。回放只提供当时存在的代码与文档，后续修复用于标签而非检索输入。

不能只标本系统召回的候选：使用不同基线候选池、维护者补充和随机抽样查漏；
对未完全穷举的真实仓库，将 recall 标明为已标注集合上的估计，说明残余覆盖限制。
真实 PR 维持自然基率；人为平衡样例用于诊断而不用于声称上线精度。

基线应包含 grep/BM25、token/AST、纯语义 embedding、现有 diff + 工具搜索 AI review、
相同 LLM/预算下的混合检索，以及所提契约方案。消融分别去掉层次、契约、配置、
依赖方向、替代方案分析；按 PR 聚类计算置信区间并报告标注一致性。

试点可先选约 30–50 个变更和 100–200 个候选关系，用于检验标注协议与失败模式；
这些数量是工程起点，不保证统计充分性。正式规模需依据阳性率、置信区间宽度和效应量确定。
历史离线评估后进行不阻塞合入的 shadow review；在独立未来 PR 上检验成本与误报。

## 可能的研究贡献与边界

值得检验的假设是：加入内核执行上下文、配置可用性和架构依赖约束，能否在相同召回量/
评论预算下提高可行动建议精度，同时保留低文本相似但可复用的能力。
另一个假设是局部替代方案证据能减少貌似合理却不可实现的建议，并降低人类核验成本。
多粒度实体/能力组匹配和多配置索引维护也是候选方向，但不是已确立的新颖点。

仅把 metadata、向量数据库、重复率、LLM 和打分串起来，现有工作重叠较多。
论文需要可复现任务定义、可靠标注及对照；专利需要针对具体技术特征逐项比对权利要求。
专利初检另见 [专利证据笔记](../prior-art/2026-10-27-patents.md)；公开文本不是完整法律状态核查。

下一轮建议先确定“什么算应该复用”的标注协议，手工走通一批正例和困难负例，
再决定 metadata 最小字段、检索粒度和评分器。当前没有固定模型、数据库或上线阈值。
