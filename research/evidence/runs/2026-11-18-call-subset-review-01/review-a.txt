case-001 — Concrete local sharing opportunity, conditional on preserving ownership and lock boundaries

Evidence/common mechanism: fs/kvfs/src/super_block.rs:168-179 (SuperBlockSet::live_super_blocks) and :1263-1273 (SuperBlock::live_inodes) both traverse a Vec of Weak references, attempt one upgrade per entry, retain successful entries, remove expired entries, and return the upgraded strong references in traversal order. This is a complete repeated collection operation, not merely common API spelling. Neither body delegates this operation to a common helper. The registry wrapper at :267-270 already delegates to SuperBlockSet, but does not share its collector with live_inodes.

Smallest seam: a private function in this same file, conceptually collect_live<T>(&mut Vec<Weak<T>>) -> Vec<Arc<T>>, owning only the retain/upgrade/collect loop. Leave both existing methods and synchronization ownership in place. No callback, registry trait, shared object model, or configuration parameter is necessary. The helper would save only one small loop; its justification is naming and centralizing the coupled pruning/pinning invariant, not an asserted performance improvement.

Necessary differences: the registry stores weak superblocks (:120-123), while each superblock stores weak inodes behind its own mutex (:544). The former method receives &mut self under an outer registry guard (:268-269); the latter acquires its guard internally (:1265). Neither collector has a Result error path or flags. Expiration is normal omission, not an error. Both mutate their respective weak lists and allocate a result vector. Preserve retained order and multiplicity; do not turn the operation into deduplication or a liveness count. Returned Arc values pin every successful upgrade until the caller drops them, including an upgrade that becomes the last strong owner. The local warning in lookup_bdev at :148-150 explicitly identifies reentrant driver release as a reason to defer drops. Synchronization happens after snapshot collection at :273-275 and :1304-1308. A helper must not consume the returned snapshot, call sync under the collection lock, perform a second upgrade, or release successful upgrades before returning. Guard release should remain before caller processing and eventual snapshot destruction on the normal path. Allocation-failure/unwind behavior and actual Mutex implementation were not established.

Existing sharing/limits: Arc/Weak and Vec::retain already implement the primitives, but the coupling of pruning with pinning remains duplicated. The neighboring lookup_bdev (:130-155) also matches filesystem/device identity and retains references for deferred release; it is outside this pair's proposed seam. No dependency search established whether a similar utility exists elsewhere.

Smallest bounded executable confirmation obligation (not run): exercise the extracted collector against the original loop with empty, all-expired, and mixed vectors containing two live identities plus a duplicate weak entry. Assert returned pointer sequence/multiplicity, retained weak sequence, and strong ownership after external owners are dropped. Add one drop-probe check around the locked wrapper: the collected value survives until the result is dropped after guard release, and its destructor can reacquire the wrapper's lock. Compile the two production call sites in the owning crate's supported test configuration to confirm guard coercions and generic bounds; a standalone collection test cannot establish those details.

case-002 — Existing delegation already shares state creation; retain distinct policy wrappers

Evidence/common mechanism: fs/kvfs/src/node/inode.rs:1468-1476 and :1823-1835 each turn one Arc<T> into three trait-object views of the same allocation by cloning twice and moving once, then forward flags and initialization data. The bounds are identical. These three conversion statements are real repeated glue, but the destination constructors intentionally differ.

Existing sharing: new_file_with_operations (:1591-1605) delegates to new_file_with_operation_tables (:1617-1654); new_dir_with_operations (:1838-1855) builds InodeParts directly. Both converge on from_parts (:1676-1680), then from_parts_with_attributes (:1701-1729). The shared implementation constructs identity and attributes, initializes locks/counters and special state, creates the cyclic inode allocation and address-space mapping, and obtains cache residency from inode_operations. Thus the substantial construction mechanism is already shared; there are not two independent implementations of inode allocation/state initialization. The no-flags openable-directory wrapper also already delegates to its flags variant (:1815-1819).

Necessary differences: the file route selects empty address-space operations for special node types and default operations otherwise (:1624-1633), normalizes non-special rdev (:1634-1639), and adds NON_CACHEABLE for regular files without ALWAYS_CACHE (:1640-1645). The directory route asserts directory mode in debug builds and always supplies empty address-space operations (:1845-1853), without that file-route flag normalization. Preserve these policies and their debug/release distinction. Neither reviewed wrapper returns Result. They transfer ownership of the same node into three interfaces; no new backing node should be allocated, and flags/init should reach the selected policy path unchanged. The shared lower constructor invokes cache_residency and allocates the mapping (:1710-1725); a refactor must not duplicate those effects or change callback order. Runtime behavior of external operation-table/address-space implementations remains unknown.

Judgment/seam: do not merge the two constructors by routing the directory constructor through the file constructor, or by adding a boolean mode selector that hides policy. A private trait-view tuple helper is mechanically possible, but adds a generic interface and tuple plumbing to replace three obvious coercions at each site. On this pair alone its interface cost outweighs the demonstrated benefit. Existing delegation solves the meaningful shared construction responsibility; no additional helper is recommended.

Smallest bounded executable confirmation obligation (not run): a focused constructor fixture with one instrumented node implementing both operation traits. Construct a regular file with empty flags, a regular file with ALWAYS_CACHE, and an openable directory; check the resulting flags, initialization fields, and address-space operation selection. Verify private-data downcast and operation callbacks refer to the same backing allocation, with cache_residency invoked once per constructed inode. A debug-only invalid-directory-mode assertion check protects the route distinction. This would confirm the observed sharing and policy differences without broad filesystem integration; available fixtures and the dependency behavior were not inspected.

case-003 — Necessary topology differences block direct substitution; generic loop extraction not justified

Evidence/common mechanism: fs/kvfs/src/node/dentry.rs:722-735 and fs/kvfs/src/mount.rs:381-392 both clone the starting node, compare identity before advancing, repeatedly take a parent, and report absence after reaching a root. Both include equality as reachable/ancestral. The arguments have opposite presentation: self is the sought ancestor in the dentry method, whereas path is the starting descendant in the mount method. A generic walk could express this skeleton, but the parent and identity operations carry distinct semantics.

Necessary differences/state: Dentry wraps an Arc<DentryInner> (dentry.rs:235-237); its parent reads the location lock and clones the parent dentry (:654-657), and its identity comparison is that Arc's identity (:778-780). Path owns both a mount Arc and a Dentry (mount.rs:851-856); its identity requires BOTH mount identity and dentry identity (:1091-1094). Path::parent (:1003-1009) follows the dentry parent within the mount, but at a mount root follows the attached location's parent across a mount boundary. Mount::location clones a mutex-protected Option<Path> (:736-739), and detach removes that location (:829-831). The same dentry in different bind mounts cannot simply be treated as the same path. Physical dentry ancestry can also extend above a bind mount's selected root, whereas path ancestry must honor that root and the attachment topology.

Errors/configuration/lifetimes/effects: is_ancestor_of exposes VfsResult<bool> but its visible implementation returns only Ok; is_reachable_from returns bool. Neither takes flags or mutates topology. Both incur reference-count operations and parent-lock reads. Path's temporary clones pin mounts as well as dentries; dentry traversal alone does not supply that ownership. Mount teardown can synchronously deactivate a superblock (mount.rs:108-111, with lifetime warning :62-64). Preserve clone/drop ordering and short-circuit equality before any parent lookup. Neither shown loop provides a whole-traversal topology snapshot or cycle detection; concurrent mutation guarantees and global acyclicity are not established by this bounded read. Do not silently add stronger locking or claim concurrency equivalence.

Existing sharing/seam: Path already delegates its within-mount step to Dentry::parent (mount.rs:1006) and the dentry portion of identity to Dentry::ptr_eq (:1093). The outer ancestry loops do not delegate to each other. Directly replacing mount reachability with dentry ancestry loses mount identity and boundary behavior. A shared loop accepting parent/equality callbacks could preserve both, so these differences do not make all abstraction impossible; however, it would abstract little beyond elementary iteration while exposing two semantic callbacks and preserving separate result wrappers. No worthwhile local helper is supported by this pair alone. Keep the domain operations distinct.

Smallest bounded executable confirmation obligation (not run): a mount/dentry fixture covering self equality, same-tree ancestor and unrelated entries, plus a bind mount rooted at a non-root dentry and an attached child mount. Assert that identical dentries in distinct mount identities do not pass path equality, that bind-root ancestry follows the attachment rather than its physical dentry parent, and that child-mount ancestry can reach the parent path. Include a detached mount/root termination case. Compare any future candidate with the existing functions on the identical fixture; a mock generic parent chain alone would miss the decisive behavior. Concurrent rename/detach correctness remains outside this bounded obligation.
