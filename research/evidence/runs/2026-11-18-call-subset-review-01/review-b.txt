case-004 — Concrete local shared implementation opportunity, conditional on preserving the transaction boundary.

Evidence/common mechanism: fs/kvfs/src/node/dentry.rs:1214-1236 (unlink_with) and :1247-1269 (rmdir_with) repeat the same substantial sequence: validate parent and name; retain parent inode; take its exclusive namespace lock; perform positive lookup; retain victim inode; reject parent/victim identity equality before taking the victim lock; perform operation-specific checks and mutation; mark the entry unlinked; invalidate its cache entry. The duplicated mechanism is the locked removal transaction, not merely similarly named calls.

Smallest plausible seam: a private removal helper taking name and one FnOnce(&VfsInode, &Dentry) -> VfsResult<()> callback. It would own both inode Arcs and both guards, perform the common validation/lookup/identity check, invoke the callback under both locks, and perform the existing success-only cleanup. Each existing wrapper would keep its type check, permission callback, and selected inode operation together in that callback. This needs no new public API or generalized namespace-operation framework. It consolidates a meaningful ordering invariant; confirmation is still needed before accepting the extra indirection.

Necessary differences: unlink rejects directories with IsADirectory (:1228-1229); rmdir rejects non-directories with NotADirectory (:1261-1262). The corresponding may_* callback must run only after that check, exactly once, and before the corresponding inode mutation (:1231-1232, :1264-1265). The rmdir documentation delegates emptiness authority to the filesystem (:1238-1241); a shared helper must not substitute a generic cached-children emptiness check. Both guards must remain alive through marking and cache invalidation; returning a victim from a setup-only helper would prematurely end the critical section. Preserve the parent-before-name validation order, positive lookup's NotFound result (:1138-1144), and InvalidInput self-alias rejection before acquiring the second lock. Permission or backend errors skip the explicit success cleanup, but this is not a promise that lookup or callbacks have no side effects or roll back their own work.

Existing sharing: verify_child_name (:415-425), lookup_positive_locked (:1138-1145), mark_unlinked (:705-707), and forget_cache_entry (:890-897) are already shared. Cache cleanup removes the parent child entry and calls superblock uncache (:875-887); for a positive directory it also recursively forgets children (:1383-1398). Keep that existing type-dependent cleanup. with_locked_child (:1147-1158) already owns parent locking for creation, but allows negative candidates and does not own the victim lock or removal cleanup; it does not already solve this pair. The cfg(unittest) convenience wrappers (:1209-1212, :1242-1245) delegate individually, while the reviewed functions themselves are not gated there.

Smallest bounded executable confirmation obligation (not run): one table-driven local removal fixture covering both operation kinds. Record permission/backend invocation order and observe the two namespace locks held at those callbacks; then assert success marks/un-caches the target and directory success preserves recursive invalidation. Include wrong victim type, negative lookup, parent/victim inode alias, permission rejection, and backend rejection; verify exact error and absence of later callbacks or success cleanup. Include one invalid-name/non-directory-parent combination to preserve error precedence. Prove locks are released after success and each failure. This validates only the proposed local seam, not whole-filesystem concurrency. Backend implementations, superblock cache internals, and namespace-lock implementation were not followed; their deeper behavior remains unknown.

case-005 — Existing delegation already shares the substantive construction; no additional helper recommended on this evidence.

Evidence/common mechanism: fs/kvfs/src/node/inode.rs:1796-1812 (new_dir_with_inode_operations) and :1838-1855 (new_dir_with_operations) both debug-assert directory mode and populate InodeParts with supplied private data, inode operations, flags, initialization, and empty address-space operations. The residual repeated work is assertion and argument packaging. InodeParts already represents optional file operations (:1352-1359). Both constructors delegate to from_parts (:1676-1680), which creates attributes and delegates to from_parts_with_attributes (:1701-1729). That common implementation owns cache-residency lookup, cyclic Arc allocation, identity and lock initialization, counters, mapping, special state, and lazy file-lock state. Those are not duplicated by this pair.

Necessary differences: the private constructor installs None (:1808), while the public explicit-table constructor requires and retains Some(file_operations) (:1841, :1850). The shared constructor resolves None using no_open_file_operations (:1719), whose open returns ENXIO (:1209-1217). Replacing absence with an arbitrary operation table changes behavior. The supplied table can instead implement its own opening behavior and state. The public generic entry points also distinguish InodeOperations-only nodes (:1766-1788) from nodes implementing FileOperations as well (:1814-1834). Preserve those bounds and ownership: move the supplied Arcs into the shared object, retain the chosen table, and do not add clones or early drops. Both return Arc<Self>, not a fallible result; directory validation is a debug assertion (:1802-1803, :1845-1846), not a release-mode rejection. No branch-specific cfg is shown in these constructors. Their common allocation/state initialization and fallback allocation are existing side effects, not work for a new helper to recreate.

A private optional-file-operations directory helper could technically remove the repeated assertion and InodeParts literal. That option is locally expressible, but it introduces another constructor layer around an already shared representation and allocation path. The observed repetition does not establish that its interface cost pays off. Keep the existing delegation and meaningful API distinction.

Smallest bounded executable confirmation obligation (not run): a paired directory-construction test using equal flags/init and a sentinel FileOperations object. Verify common identity/type/attribute initialization, preservation of supplied private-data and operation-object identity, ENXIO when opening the no-file-operations variant, and invocation of the sentinel table in the explicit variant. If an extraction is nevertheless proposed, compare the same fixture before/after and retain the debug-only invalid-mode assertion behavior. No broader filesystem test is required to assess this narrow packaging change. AddressSpace implementation, attribute-construction internals, and external operation-trait defaults were not followed; no claims about their full behavior are made.

case-006 — Common presentation pattern, but necessary acquisition differences and tiny residual body favor retaining separate formatters.

Evidence/common mechanism: task/kspin/src/rwlock.rs:225-238 and task/kspin/src/lock.rs:253-263 each make one nonblocking acquisition attempt, format a named debug struct with a data field while holding the guard, or print the string "<locked>" when acquisition fails. Both propagate fmt::Result from finish. This is actual repeated presentation control flow, but most rendering is already delegated to core::fmt's debug_struct/field/finish. The observed code does not establish a worthwhile new shared lock abstraction.

Necessary differences: the read/write lock uses try_read, which checks writer ownership and reader saturation and performs a single reader-count CAS (rwlock.rs:137-157). It can format during an existing read lock and can fail a raced CAS without persistent writer ownership. The exclusive lock uses try_lock (lock.rs:192-220): with smp it CASes a Boolean; without smp it takes the success path unconditionally (:201-202). Thus the placeholder reports failed acquisition, not a universal proof that the lock is held. Struct names must remain SpinRwLock and SpinLock. The success branch's &&*guard supports unsized Debug payloads, and the guard must survive the complete field/finish sequence, including formatting errors. Read-guard drop decrements reader count then releases execution-context state (rwlock.rs:283-288); exclusive-guard drop clears the flag only under smp then releases execution-context state (lock.rs:304-311). Acquisition failure already releases that state before placeholder formatting. With stats enabled, each successful attempt records an acquisition, including one made solely for Debug (rwlock.rs:147-155, :299-307; lock.rs:204-218, :291-301). A helper must not add retries, blocking, preflight is_locked checks, extra acquisitions, or change these side effects.

Existing sharing: the acquisition and RAII implementations already encapsulate their distinct state protocols, and individual guard Debug implementations delegate payload formatting (rwlock.rs:271-280; lock.rs:285-288). No common wrapper-formatting helper is visible in the two complete supplied files. A private formatter receiving a label and an owned optional dereferenceable guard could share the match without merging acquisition, but needs generic lifetime/unsized support and cross-module placement merely to remove two short branches. Retaining separate formatters is the bounded recommendation; necessary acquisition differences block treating the complete paths as interchangeable, not every possible presentation-only extraction.

Smallest bounded executable confirmation obligation (not run): a focused formatter fixture with a recording BaseGuard and Debug payload, covering free locks, an rwlock with an existing reader, an rwlock with a writer, and an smp exclusive lock already held. Assert exact normal/alternate Debug output, one acquisition attempt, balanced execution-context acquire/release, and lock availability after completion. A failing formatter sink must also leave the newly acquired guard released; an unsized Debug payload must compile. Check smp on/off and stats on/off if any helper is proposed, keeping the non-smp held-lock case out of a fixture that assumes exclusive rejection. Verify successful Debug increments acquisition statistics once and failures do not. BaseGuard implementations, hardware context effects, and klockstat internals are outside the inspected files and remain unknown; a recording stub can confirm local ordering only.
