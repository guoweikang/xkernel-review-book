3. Does var mean binding? No: a syntactic marker and spelling heuristic
Java ConvertJava.localVarContexts (42–44) lists variableDeclaratorId, primary, catchClause, lambdaParameters. In getSerializedTree (about251–260), an identifier/literal-classified token receives var=true when its parser rule is in that list. No declaration-resolution object or lexical scope ID is stored in the provided JSON.
Python collect_features_aux checks presence of "var", not boolean truth of its value, and checks not token[0].isupper(). Consequently even {"var":false} would still pass that presence test; a control must preserve marker presence/value rather than assume false disables it.
For eligible leaves, normalized token is #VAR but the same-use dictionary key is the original token string. Its lifetime is one collect_features_as_list traversal, not a lexical block; shadowed same-spelling entities can be conflated, aliases are not resolved. Unbound fixture list is nevertheless marked var: marking is not a declaration proof.
get_var_context special-cases #.# by looking at the subtree two positions after the receiver and returning its leftmost raw leaf token. On this fixture those are method names iterator/hasNext/next. Else it uses the immediate parent label plus child index.
Therefore this mechanism can distinguish allocation of spelling-equal occurrences to local contexts; it does NOT establish binding identity, reaching definitions, ownership, execution order or valid API receiver types.

4. Eligible original API paths for a future frozen control
Preferred narrow original-function entry:
  collect_features_as_list(deepcopy(record["ast"]), is_init=True, is_counter=False)
  -> (list[int] feature occurrence IDs, None)
  then original vocab.get_word(id) -> list[str].
It initializes fresh traversal stacks, same-spelling dictionary and leaf_idx=0 each call. A surrounding driver must provide the original function's module-global config=Config() and vocab=Vocab(); do not implement substitute feature rules.

Vocabulary discipline is essential:
- Fresh Vocab per variant plus immediate decoding with THAT vocabulary allows comparing string lists/Counters. Do not compare independently allocated integer IDs.
- Or grow one shared Vocab with is_init=True for every variant, recording the input order and comparing decoded strings. This is a controlled feature study, not train/held-out retrieval.
- Query path is_init=False with a vocab built only on baseline maps newly introduced context features to NUM_FEATURE_MIN (10)/#UNK. That can hide differences. append_feature_index and append_feature_pair also compare integer n with str(NUM_FEATURE_MIN), so that guard does not reliably remove that integer unknown value. Do not patch it here; avoid this confound in raw-feature controls by the declared is_init=True route.
- If specifically testing fixed-index query behavior later, is_init=False is legitimate but report unknown counts/identity collapse separately; it is a different question.
- is_counter=True returns (list[Counter], dict) for per-leaf aggregation, NOT the same flat-list type. append_feature_pair increments counters at both endpoints. In the inspected code leaf_pair_features is initialized and passed but not populated by append_feature_pair; do not advertise a ready-made pair-to-source provenance map from that dict. The flat list route is the minimal eligible interface.
- distance(Counter(decodedA),Counter(decodedB)) is available for nonempty inputs, but exact normalized list/Counter equality and differences are the direct control measures; no retrieval ranking needed.

5. Control eligibility, not results
A. Consistent lowercase var renaming on a deepcopy of this fixture
Permitted transformation: a bijection on the fixture's selected raw lowercase variable spellings, applied consistently to all and only corresponding var-marked leaf tokens. Preserve tree/label/leaf/var/line/leading/trailing fields, method/type tokens and occurrence equality partition; avoid empty names, uppercase starts, name merging or collisions with unaffected variables.
Static expectation under the stated default and THIS fixture: normalized token/parent/sibling features unchanged; same-spelling partition unchanged; member-context names remain unchanged, so decoded feature occurrences should be invariant. This is an expected property to test, not a reported run.
Limit: for arbitrary JSON, get_leftmost_leaf may return another renamed raw token in a context position; invariance is not universal without examining those contexts. Consistent spelling rename is not proof of capture-avoiding alpha-renaming in a real compiler. Shadowing and externally bound identifiers remain outside this fixture control.

B. Reassigned variable uses with identical invocation/token multiset
A global bijection like A merely renames spellings; it is NOT reassignment. For a discriminating representation control, keep declaration spellings fixed and permute selected receiver-use tokens, preserving raw token multiplicities, all unmarked API invocation tokens, tree structure and the locations/markers of the variable leaves. Then normalized token/parent/ordinary-sibling features can remain the same while the same-spelling context histories change.
The official fixture has only one itr chain, one list receiver and unused strBuf. Swapping the two different-spelling use positions (list at iterator receiver and itr at next receiver) is structurally expressible without inventing AST nodes and preserves their token multiset; swapping the two itr receiver tokens is a no-op. BUT the different-spelling swap can introduce an uninitialized/self-referential itr use and incompatible list.next receiver. It is ONLY a symbolic representation control, not a valid Java behavior control or kernel example. This is a candidate transformation for main's decision, not executed or mandated.
If the intended question demands two semantically valid independent iterator receivers, this supplied fixture cannot establish that; additional authorized original data/type evidence is required. Do not fabricate an AST to fill the gap or call symbolic sensitivity semantic correctness.
Required invariants to freeze before any run: exact changed leaf positions; equal all-token and unmarked-invocation Counters; preserved AST topology/labels/metadata; variable occurrence partition genuinely changed; default Config unchanged; output type and vocabulary policy fixed. Only then compare decoded feature family differences. No expectation that every reassignment is detectable: identical local contexts, limited two-use history and bag collisions can erase distinctions.

6. Scope of useful obligations
A successful A/B control would only support that this official spelling-context mechanism is insensitive to a declared renaming and sensitive to particular receiver-use redistribution beyond same-API coincidence. It would not establish actual local binding/dataflow, extractability, absence of existing delegation, Rust compatibility, useful ranking or refactoring gain.
Static mismatch provenance is only partly resolved: current code/input explain current family counts and examples; official55 origin remains unknown. Stop here; no source/config/control runs or fourth source needed.
