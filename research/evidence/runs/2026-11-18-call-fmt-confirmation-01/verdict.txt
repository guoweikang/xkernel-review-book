case-006 bounded confirmation — reject extraction as not simpler

Decision
Keep the two small Debug implementations as they are. A shared presentation helper is statically plausible, but the concrete extraction does not improve the responsibility boundary enough to justify its interface and indirection. This is the Stage A simplicity rejection specified in protocol.txt, not a claim that equivalence tests failed. No runtime equivalence tests were run, and no matched-output/error result is claimed. The earlier review's permission to investigate a local opportunity is now resolved negatively for this exact two-caller proposal.

Why reject
The original already delegates the difficult, stateful part to Once::get (lazy.rs:77; once.rs:66,486–497). Each presentation body has five substantive operation lines: construct standard DebugTuple, match, two arms, finish. The remaining choices are precisely the type-local label and absent-value text. The helper removes one duplicated branch expression, but asks a reader to follow a cross-module generic three-argument interface to understand five lines of standard builder usage. It also makes DebugTuple and its two lifetime slots part of an internal seam. Labels and absence markers still need to be selected correctly at both call sites, so the abstraction does not eliminate the policy that needs review.
The candidate saves two body operation lines across the pair while increasing counted LOC by three and introducing a new internal symbol. This numerical increase is supporting evidence, not the sole reason for rejection: even compressing the helper signature onto one long line would not remove the extra interface, caller choices or navigation. There are only these two Debug implementations in the complete provided production crate sources; no additional caller justifies a shared presentation concept in this bounded task.
Alternative considered: fn fmt_value<T: Debug>(formatter: &mut Formatter<'_>, value: Option<&T>, name: &str, empty: &str) -> fmt::Result hides tuple creation as well, at the cost of four parameters and two string policies. Passing get() eagerly to that helper moves the state read before debug_tuple construction, unlike the original. That ordering may be immaterial for ordinary output but is unnecessary uncertainty here. Restoring the ordering requires the pre-created tuple used by the concrete candidate, or a callback/interface expansion. A Once method accepting formatter/name/marker could keep ordering internally, but still adds a presentation API to the storage abstraction and a label/marker contract; it does not remove the same design cost. Macros, traits or new wrapper types would add still more machinery. None is needed to complete this confirmation.

Contract feasibility (static reasoning; NOT execution results)
1. Labels: LazyValue at lazy.rs:74 and OnceCell at once.rs:64 remain at the caller's debug_tuple construction. Direct delegation to Once::fmt would change Lazy's outer label and missing-value spelling; it is not equivalent.
2. Noquote placeholders: lazy.rs:79 and once.rs:68 use Debug of format_args!, not Debug of &str. The candidate keeps format_args!("{empty}") as the field, intending the same literal bytes without quotes for <uninit>/<not-ready>. It never passes empty itself as a Debug field. Actual ordinary/alternate byte equivalence was not measured.
3. Single get and order: proposed callers each construct the tuple and then call get once. The helper only consumes Option<&T>. It has no access to the container, no second state read and no force/poll/wait. Once::get uses one Acquire load and returns Some only for Ready (once.rs:486–497). No status distinction is added: Initializing, Failed and Uninitialized still arrive as None. No concurrent execution or synchronization change was attempted.
4. T formatting and errors: Some still passes &value, where value is &T, into the same DebugTuple::field operation. There is no stringify, catch, unwrap or intermediate allocated buffer. finish returns fmt::Result directly. The intended T::fmt dispatch, writer error propagation and alternate flag behavior stay with the existing core builder. A failing writer may prevent T::fmt from being invoked; no unconditional “T formats once” claim is made. The candidate introduces no explicit extra T formatting. Byte/error equality, partial writes and alternate nested formatting remain untested, rather than being inferred from the static shape assertions in checks.log.
5. Bounds: original Lazy Debug is impl<T: fmt::Debug, F>, with no F bound (lazy.rs:71); candidate preserves it. Helper mentions T only. It does not read factory (lazy.rs:68) or enter force (138–148). A non-Debug, non-callable F should remain admissible on this static design, but no compiler check was run. Once's Debug bound is unchanged (once.rs:61).
6. Placement/no_std: lib.rs:19,26–30 permits a sibling-visible helper using existing core::fmt imports (lazy.rs:12; once.rs:9–14); no std or allocation dependency is introduced in the text. Actual compiler/toolchain compatibility remains untested. Cargo.toml:3–11 inherits workspace metadata and :13–18 dependencies/lints; workspace configuration was not expanded because Stage B was rejected.
