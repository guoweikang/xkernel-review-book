case-004 — necessary_difference
The repeated shape is a location read guard followed by a directory-operation
dispatch, not two independent implementations of node creation. Both already
delegate operation availability to require_directory_operations, which returns
NotADirectory (fs/kvfs/src/node/inode.rs:2166-2171), and location locking to
Dentry::lock_location (fs/kvfs/src/node/dentry.rs:709-714). The local guard spans
the filesystem callback in both wrappers (inode.rs:2209-2217,2266-2268).
The meaningful residual difference is the operation contract: create receives
exclusive: bool; mknod receives DeviceId. They invoke different trait methods,
whose defaults even return different errors: create -> PermissionDenied
(inode.rs:175-185), mknod -> OperationNotPermitted (inode.rs:226-236).
Both borrow the locked dentry and credentials and return VfsResult<()> without
translating backend errors. A generic closure wrapper could factor a few lines,
but the evidence shows no independent common creation mechanism needing that
additional boundary. Keep distinct dispatch and arguments, the shared helper's
NotADirectory error, guard lifetime, and each backend's error unchanged. No
confirmation candidate is proposed for this pair.

case-005 — confirmation_candidate (partial overlap)
Already shared: directory/name validation, exclusive namespace locking, final
lookup, and callback execution under the guard are in with_locked_child
(fs/kvfs/src/node/dentry.rs:1147-1158); lookup/cache mechanics are in
lookup_locked (dentry.rs:1073-1136). Do not count these as independent duplicate
mechanisms. Name validation preserves InvalidInput/NameTooLong distinctions
(dentry.rs:415-425).
Independent residual overlap: both closures reject an already attached inode
when exclusive, call the FnOnce callback, propagate its failure, reject a
still-negative dentry with InvalidInput, then clone that same candidate
(dentry.rs:1170-1179 versus 1191-1205). This is a small creation-completion
protocol, not merely a shared list of calls. The right side generalizes it by
returning Existing on a positive nonexclusive lookup and tagging successful
creation Created. The result enum is defined at dentry.rs:258-261.
Smallest boundary: make create_exclusive_with delegate to the existing
lookup_or_create_with(name, true, create_fn) and adapt the owned enum payload to
Dentry. No new common helper or new lock is needed. The exclusive call can only
produce Created on success according to the existing branch; keep the enum
conversion local without adding an observable error or panic policy. Preserve
the public/internal signatures, FnOnce ownership, original candidate identity,
and nonexclusive Existing/Created distinction in lookup_or_create_with.
Do not conflate is_really_positive (inode attachment) with !is_negative (type
flags): their definitions differ at dentry.rs:538-555, and the existing protocol
deliberately uses different predicates before and after the callback.
ONE adoption-changing obligation: establish observational equivalence of the
exclusive adapter to the current create_exclusive_with protocol. This includes
AlreadyExists before callback invocation, exactly one callback on a missing
candidate while the parent namespace guard remains held, unchanged callback
errors, InvalidInput on success without instantiation, and the same returned
dentry identity on success. These are facets of one protocol-equivalence gate;
if delegation changes any of them, do not adopt it.
Existing verification entry: no suitable entry identified in the inspected
source scope. The supplied files contain no discovered test entry exercising
this protocol; cfg(unittest) helper methods are not evidence of such a test.
No external test files were opened or test coverage assumed. The lack of a
verified entry keeps this a confirmation candidate, not an approved refactor.

case-006 — already_shared
Both Path methods already delegate the substantive name/existence/serialization
and completion protocol to Dentry::create_exclusive_with
(fs/kvfs/src/mount.rs:1467-1475,1492-1507; fs/kvfs/src/node/dentry.rs:1165-1180).
Their repeated as_dir/callback/map shape is adapter glue around that shared
mechanism. with_dentry preserves the mount by cloning its Arc and takes ownership
of the returned Dentry (mount.rs:873-875). The duplicated internals noted in
case-005 belong to that lower-layer pair, not independent implementations here.
Keep the operation-specific callbacks: vfs_create checks mount writability and
directory permission, prepares regular-file mode, and forwards exclusive=true
from Path::create (mount.rs:1343-1362,1472). vfs_mknod uses the requested node type
and device, with device-access policy followed by CAP_MKNOD checking for character
and block devices, then mode preparation and mknod dispatch
(mount.rs:1364-1394). Both pass an empty umask here. Do not hoist these callbacks'
authorization outside the existing final-lookup lock: a positive child currently
returns AlreadyExists before create-only authorization runs. Backend operation,
device/type handling, error ordering, and mount/dentry ownership remain necessary
differences. No further common boundary is warranted by this pair.
