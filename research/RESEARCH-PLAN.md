# 研究计划：约束感知的功能重叠识别与公共抽象建议

版本：v0.2，2026-10-27。保留用户同意的原六阶段，当前仅执行 A 基础调研；具体方法、样本量和
实验协议仍为提案，不是创新性结论或实现效果承诺。
用户要求以科研方式持续调研、开发并在真实场景验证，为论文及专利积累核心技术证据。

## 1. 研究定位

目标是从真实软件仓库发现功能重叠和共同机制，提出可实施、可验证、值得维护者采用的
复用或公共抽象方案。覆盖完整存量仓库与增量变更；AI review 是输出渠道之一。
公共抽象可以尚不存在，结果可以是多个实现共享机制、通过 Rust 类型/泛型/trait/组合
保留定制差异，而不是只找一个已有函数替换另一个。

科研主线：问题证据 → 最近已有工作 → 可证伪假设 → 最小方法 → 独立评估 → 真实改造。
工程主线服务上述验证；索引数据库、模型编排和 review 接入本身不预设为创新。
不以保证论文录用或专利授权为目标承诺，也不为支持预期结论隐去反例。

## 2. 当前证据支持到哪里

### 学习范围补充（2026-10-28，用户授权）

用户愿意扩大学习范围，以全面理解 AI review，而不局限于重复功能评价。
此补充扩大基础调研的学习视野，不替换原六阶段，不自动扩大系统开发或论文实现目标。
重复功能识别、公共抽象和优化建议仍是当前项目主线；通用 PR 评审系统不是新增实现承诺。

采用以下教学地图（组织框架，不是已验证的领域分类或创新结论）：

| 学习主题 | 核心问题 | 与当前研究的联系 |
| --- | --- | --- |
| 质量目标与任务类型 | 合规检查、缺陷发现、质量取舍和合入决策有何区别 | 不把重复率或质量总分当唯一目标 |
| 上下文与证据 | 如何结合 diff、需求、调用方、配置、评审历史与工具输出 | 语义 metadata 的作用及边界 |
| 方法与验证 | 规则、静态分析、检索、模型、执行验证如何分工 | 抽象的可行性与行为/性能证据 |
| 评价系统 | 标签从哪里来，怎样测误报、漏报、可行动性、校准与成本 | Themis、CodeTaste 及历史偏好候选 |
| 人机协作 | 评论是否值得提出，如何表达不确定性与处理分歧 | 建议质量不等同评论采纳率 |
| 工程可信性 | 权限、仓库内容提示注入、版本隔离、隐私和结果失效 | 后续全仓及增量旁路运行 |

阅读顺序建议：继续 Themis §3 的偏好标签来源 → 对照 CodeTaste 的历史选择一致性 →
专题学习 AI review 的上下文、评论价值和人机协作 → 回到 Rust 抽象与验证。
每篇保留通用启示、项目关联、证据限制及待查新点，避免同时展开过多路线。

这是初步问题地图，不是已完成系统性综述。已有来源的阅读范围在 [SOURCES](SOURCES.md)。

| 研究路线 | 已有能力/证据 | 本项目应研究的差距，及证据边界 |
| --- | --- | --- |
| token/AST/图/语义向量检测 | [SourcererCC](https://arxiv.org/abs/1512.06448) 等研究已提供克隆发现能力 | 检测重叠并不自动产生可实施抽象；不能把 Rust 接入本身当作方法创新 |
| 克隆重构推荐 | [设计、上下文与历史推荐](https://cormack.uwaterloo.ca/~migod/papers/2014/icsme14-wei.pdf) 已研究哪些克隆值得重构 | “加上下文打分”不新；需对比具体约束表示、候选生成和判定机制 |
| 仓库级重构 | [SWE-Refactor v1](https://arxiv.org/html/2602.03712v1) 给定目标方法和重构类型，含 Java 原子及复合任务 | 不能据此宣称现有工作只看片段；自主发现多实现共同抽象是不同任务，是否有其他工作完整覆盖仍需检索 |
| 多文件代理执行 | [RefactorBench](https://arxiv.org/abs/2503.07832) 摘要描述组合任务与状态跟踪挑战 | 计划/执行/验证也有既有研究；本轮仅读摘要，不援引其结果推断 Rust 效果 |
| 语义真值与评测 | [BigCloneBench 使用问题研究](https://arxiv.org/html/2505.04311v1) 对抽样 WT3/T4 标签提出质疑 | 克隆标签不能直接充当“值得抽象”的真值；其结论不能外推整个数据集或所有基准 |
| 稳健性 | [2026 语义克隆预印本](https://arxiv.org/html/2606.25272v1) 报告变换后退化，且承认变换无形式化保证、仅测 BigCloneBench | 既要研究检测器的稳健性，也要核验测试变换是否真的保持语义；不是已证实的 X-Kernel 缺陷 |

补充正文核对见 [公共抽象与 Rust 重构专题](notes/2026-10-27-abstraction-prior-work.md)：
[Wrangler](https://www.cs.kent.ac.uk/pubs/2011/3087/) 已覆盖公共函数与差异参数化、克隆类和增量分析；
[Stitch](https://arxiv.org/html/2211.16605v2) 已研究从程序语料学习抽象库；
[REM](https://verse-lab.org/papers/rem-oopsla23.pdf) 与
[REM2.0 v1](https://arxiv.org/html/2601.19207v1) 已处理 Rust 抽取修复及受限子集等价验证。
具体可追查的障碍包括候选密度成本、过度泛化、签名修复失败和验证子集限制。
这些均有已有解法或适用条件，H1/H2 必须逐项对比，不能以“公共骨架”或“Rust 验证”为新颖点。
更广的 anti-unification、可变部分参数化和受约束重构路线仍须补查。
“没有在当前笔记中发现”不等于文献不存在；“论文未评测该场景”不等于方法不能支持。

## 3. 基础调研工作包

调研不只收集文章数量。六条线并行形成技术地图：

1. 克隆/语义重叠：token、AST、PDG、表示学习、执行语义；部分重叠与多实体组合。
2. 抽象与复用：anti-unification、程序归纳、库学习、克隆重构、泛型/trait 参数化。
3. 可行性与正确性：所有权/借用、生命周期、别名、副作用、并发、配置与跨模块依赖。
4. 建议生成与验证：传统重构工具、LLM/工具混合方法、反例反馈、测试和局部形式化验证。
5. 评测与工程：标签可信度、低基率、数据泄漏、维护收益、增量一致性和成本。
6. 专利与技术差异：不仅搜索代码检索，还覆盖公共抽象生成、变换约束、验证反馈及排序。

执行协议：

- 先确定检索词/同义词、数据库入口和纳入排除规则；保留检索日期、候选和排除理由。
- 以作者原文/代码/数据为证据；综述用于找线索，关键结论回查原研究。
- 对最近邻工作做前向/后向引文追踪，区分同行评审、预印本、工具声明、专利公开文本。
- 每篇最近邻建立卡片：任务、输入、表示、方法、约束、输出、语言、数据、指标、复现状态、局限。
- 区分作者承认的局限、我们复现的失败、我们尚未验证的适用性推断。
- 在主要路线有代表工作且最近邻完成正文核对后形成首版综述；遗漏与无法访问项显式列出。
  连续补查未改变技术地图只作为阶段收敛信号，不是穷尽或新颖性的证明。

阶段产物：技术谱系、最近邻差异表、失败模式表、可复现性清单及逐项专利技术特征比较。
目前已有调研是种子材料，尚未达到这一完成标准。

## 4. 建议聚焦的科学问题

### RQ1：怎样从“相似代码”走向“可共同维护的能力”？

候选单位不只是一对函数，还包括部分实现、多个实体和它们的调用/状态关系。
拟表达一个候选为：实现集合、共同职责、差异职责、约束、证据、候选公共接口。
代码、文档和模型推断分层记录；契约缺失是 unknown，而不是默认兼容。

H1：在相同候选和核验预算下，显式表示共同机制、定制差异及使用约束，比仅相似度排序
或把同样材料直接交给 LLM，能提高可行抽象建议的精度，并保留足够的有效覆盖率。

反证条件：优势只来自额外上下文/预算，或通过几乎全部弃答才降低误报，或移除结构化
表示后效果不变。此时不把该表示包装成核心贡献。

### RQ2：怎样生成“公共实现 + 定制部分”而不抹掉语义差异？

候选方法提案：先对齐职责和不变量，生成少量公共接口及差异承载方案；对每个方案产生
验证义务，利用编译/类型检查、配置检查、测试或局部反例排除不适用方案，再修正接口。
需要比较直接复用、局部提取、trait+具体类型、泛型、组合与保留独立实现，不只生成一种。

H2：相比同预算的普通生成—编译—修复，显式的约束/验证义务驱动方案搜索能提升
多调用方、跨配置公共抽象的有效成功率，降低破坏行为或过度抽象的建议比例。

反证条件：通过率增益不能在独立测试中保持，额外验证成本超过人工收益，或最近工作
已经完整覆盖该机制而我们没有实质差异。编译成功与已有测试通过不构成普遍等价证明。

### RQ3：怎样评价“值得优化”，而不奖励代码行减少？

建立可争议、可仲裁的标签体系，允许多个正确方案；不要求生成代码与历史补丁相同。
建议质量至少分别记录可行性、行为证据、共同职责是否清晰、迁移负担和维护者核验成本。

H3：相同人工时间预算下，证据完整且保留反例/未知项的建议能增加被独立确认的有效
优化数，降低无效核验耗时。维护者接受率是辅助结果，不能替代正确性。

优先以 H1/H2 的一个可验证技术机制为论文核心，H3 和数据集为证据基础；
不同时承诺解决所有粒度、全部内核契约、全生态检索和自动端到端重构。

## 5. 技术路线与实现边界

统一分析流水线：固定版本/配置 → 代码事实和证据索引 → 多路候选召回 → 能力组与差异对齐
→ 约束分析 → 公共抽象/复用候选 → 验证与反例 → 优化排序和报告。

- 全仓库入口生成能力组与技术债报告；增量入口分析变更及受影响关系，不要求输入 diff 才能工作。
- 索引事实至少能回溯版本、符号、源位置和配置；摘要变更需考虑依赖和契约失效。
- 硬冲突、可适配差异、未知项分开；未知不可被高相似度抵消。
- 具体存储和 xerj 等后端可替换，先用最小原型回答科学问题，不先建设大型平台。
- 第一轮可先人工构造小批证据完整的 metadata，估计方法上限与信息需求；
  该 oracle/人工条件必须单列，最终端到端评测包括自动抽取误差和人工成本。
- 暂不自动修改生产代码，不自动阻塞合入；验证补丁在隔离 worktree 中进行，保留失败轨迹。

## 6. 真实场景与数据设计

以下是采样方向，不是已经发现重复问题：

| 场景 | 要验证的能力 | 必须包含的反例 |
| --- | --- | --- |
| 工具/格式转换/资源操作 | 直接复用与部分共同机制 | 外观相似但格式、不变量或错误语义不同 |
| 多驱动/多平台实现 | 公共机制加具体类型或 trait 实现 | 硬件语义、生命周期、分层隔离确有差异 |
| 同步/任务/队列相关实现 | 并发和执行上下文约束 | 可睡眠与中断上下文等限制使直接合并不成立 |
| Kconfig 控制的实现 | 配置条件下的可用性及公共抽象 | 互斥配置仍可能值得共享，也可能是合理独立实现 |

数据分三层：

1. 诊断集：正例、困难负例、部分重叠、三份以上能力组、unknown；用于查失败模式。
2. 自然分布集：固定版本全仓库的分层抽样区域与未来变更；用于实际精度/成本评价。
3. 真实改造集：维护者认可的候选，实施最小补丁并验证；失败和撤回同样保存。

先做约 12–20 个证据完整案例来修订协议，不宣称统计充分；正式规模根据试点的基率、
效应量、标注成本和目标区间宽度制定，在最终测试前冻结。
历史重构和维护者推荐是候选来源，不是自动真值；未改过的代码不自动为负例。

两位维护者独立标注、仲裁并记录理由；对多个合理方案允许集合标签。
候选池结合独立工具、人工查找和随机抽样，不能只标本系统召回结果。
部分重叠可能不满足传递性，不能用简单连通分量充当“共同可抽象”的真值。
按能力家族、子系统、时间分组切分，历史回放只暴露当时的信息；测试集不用于调阈值。
未来自然变更用于减轻公开历史可能进入模型训练数据的污染风险，但不宣称污染可完全排除。

## 7. 基线、消融与成功标准

基线：词法检索；token/AST 克隆；语义向量；混合检索+同一 LLM；适用语言的传统
克隆重构/抽象方法；同预算的普通工具型代理。Rust 端适配需单独报告，不能把无法运行
的 Java 工具记为零分来制造优势；公共数据上比较算法，Rust 上比较可运行系统。

两类实验分开：固定候选集比较判定/生成机制；端到端比较召回、抽取、验证和成本。
消融：移除约束、配置、差异表示、组级分析或验证反馈；另设人工准确 metadata 上限。
控制模型版本、可见代码/文档、候选规模和计算预算；报告真实额外开销及多次运行波动。

| 层次 | 核心结果 | 防止误导 |
| --- | --- | --- |
| 发现 | 已标注集上的 recall@K、能力组覆盖、部分职责定位 | 非穷举仓库不声称完整召回率 |
| 判定 | 有效建议精度、困难负例误报、弃答风险—覆盖曲线 | 分开报告低基率与平衡诊断集 |
| 优化 | 满足约束且实现预期抽象的比例、独立测试/验证结果 | 编译/测试/结构目标分别报告，非单一通过分 |
| 人工价值 | 每核验小时确认的有效优化数、核验/迁移时间、拒绝理由 | 盲化方法来源并平衡任务顺序；不能把不采纳当错误 |
| 系统成本 | 全仓扫描、增量更新、失效恢复、模型费用与资源 | 建索引成本和人工维护 metadata 成本计入 |

提前指定主要终点与最小有意义效应，再选样本量。按仓库/能力家族或任务聚类估计区间，
避免大量相关函数对制造虚假样本量；多个假设区分确认性与探索性分析。
长期维护收益无法在短期充分测量：短期只能报告结构代理指标和维护者判断，后续跟踪
共同修改、缺陷、回退等观察结果；不能将简单前后变化直接解释为因果收益。

X-Kernel 验证遵循仓库 Makefile/Kconfig 构建流程，覆盖选定配置、相关测试及所需 QEMU/
真实硬件实验。性能敏感样例比较吞吐/延迟/代码体积等，并记录环境与测量波动。
真实工程对象包括 X-Kernel、ArceOS、Starry、星绽等候选 Rust OS，不把其他项目仅作为
事后附加展示。后续核实仓库身份、版本与共享代码/派生关系，避免同源数据跨集合泄漏。
受控构造案例用于机制分析，真实项目用于外部有效性，实际重构用于落地验证，三者不替代。
这些均是后续阶段安排；当前不采集新案例或运行实验。

## 8. 分阶段推进与退出条件

按证据完成度推进，而不是承诺缺乏资源依据的日期。调研贯穿全程，第一阶段集中投入。

| 阶段 | 必交付产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| A 基础调研 | 技术地图、最近邻正文卡片、专利差异表、失败模式与复现清单 | 能指出具体问题、已有解法及未解决证据；不以“没人做过”代替检索 |
| B 真实案例试点 | 多 Rust OS 的首批 12–20 个案例、标注草案、约束证据 | 维护者能稳定区分合理独立与可优化；高分歧先修订定义 |
| C 基线复现 | 可运行基线、使用/配置核验、受控及真实案例的失败记录 | 找到可复现的现有方法失败，排除安装、适配或使用错误 |
| D 核心方法实验 | 一个聚焦机制、受控变量实验、同预算对照、消融与独立真实测试 | 提升达到事先定义的意义且没有不可接受的安全/成本代价；否则缩小或否定假设 |
| E 真实场景验证 | 多项目全仓扫描、真实重构补丁、跨配置验证、增量旁路观察 | 证明建议可落地，保存失败和保留独立的案例；不要求所有建议合入 |
| F 研究产出 | 可复现论文证据、技术交底材料、失败与负结果记录 | 每项主张能回溯方法、对照、数据和局限；发布范围经用户确认 |

研究投入优先级：先把最近邻和反例做扎实，再扩展索引平台；不以快速写完系统作为阶段成功。
